# Prompt 01: 진행 순서와 판정 기준

task-01(admin ↔ api-agent 시각화)을 아래 순서·기준으로 진행한다.

## 1단계 — 케이스 도출 (코드 전수 대조)
- 백엔드에서: `AgentExecutionResult`·`ChartData`의 모든 필드와 생성 경로(success/failure),
  chartData가 채워지는 로직을 추적해 **응답이 가질 수 있는 형태**를 나열한다.
- 프런트에서: `agent-chart.tsx`·`chart-section.tsx`·`agent-message-area.tsx`의
  **모든 조건 분기**(chartType 판별, 빈 데이터, 실패 응답, 로딩·빈 상태)를 추출한다.
- 두 목록을 교차해 케이스 매트릭스를 만든다. 형식:
  `케이스ID | 입력(요청/응답 JSON 요지) | 기대 렌더링 | 확인 방법 | 결과`.
- 판정 기준: 코드 분기 중 매트릭스에 대응 행이 없는 것이 하나라도 남으면 1단계 미완.
- 백엔드가 만들 수 있는데 프런트가 처리하지 않는 형태(또는 그 반대)는
  "불일치 후보"로 별도 표시한다 — 2단계 개선 대상의 씨앗이다.

## 2단계 — 검증 환경
- 실행 구성은 각 저장소 CLAUDE.md를 따른다: 백엔드 `docker compose up -d` 후
  필요한 서비스 bootRun(api-agent 8086, 외부 트래픽은 api-gateway 8081 경유가 원칙 —
  admin이 실제로 어느 경로로 호출하는지 admin 코드·env에서 먼저 확인), admin은 포트 3001.
- 각 케이스의 재현 방법을 정한다: 조회 케이스는 준비된 세션 데이터로, `run` 케이스는
  chartData 형태별로 유도할 수 있는 최소 프롬프트로. LLM 호출은 케이스당 최소화한다.
- **브라우저 검증 도구**: playwright MCP 도구(페이지 이동·클릭·입력·스냅샷·스크린샷)를 쓴다
  (이 프로젝트에 등록돼 있음). admin 로그인 → `/agent` 화면 진입 → 케이스 재현 → 렌더링된
  차트 SVG를 스냅샷·스크린샷으로 확인한다. 도구가 세션에 없으면 진행하지 말고 사람에게 알린다.
- **관리자 계정**: 로그인 자격은 실행 시 사용자에게 받는다(문서·코드에 비밀번호를 적지 않는다).

## 3단계 — 검증·개선 루프 (케이스 단위)
케이스마다: 브라우저 렌더링 확인 → 기대와 다르면 원인을 한쪽으로 확정
(응답 데이터가 틀림=백엔드 / 데이터는 맞는데 그리기가 틀림=프런트) → **최소 수정** →
해당 케이스 재확인 + 이미 통과한 케이스 회귀 확인 → 매트릭스의 결과 칸 갱신.
- 수정 판정 기준: 그 수정을 빼면 해당 케이스가 기대값으로 렌더링되지 않아야 한다
  (요구 밖 리팩토링 금지).
- 백엔드 수정은 파이프라인 worktree 브랜치에 테스트와 함께 커밋.
  프런트 수정은 tech-n-ai-frontend 저장소의 별도 브랜치에 커밋(admin/CLAUDE.md 규약).

## 4단계 — 성공 기준 (전부 충족해야 완료)
- 매트릭스의 모든 케이스가 결과 칸에 "기대값 렌더링 확인"으로 채워졌다.
- 백엔드: 영향 모듈 `./gradlew :{module}:test` 전부 그린.
- 프런트: `npm run lint`·`npm run build` 통과.
- 케이스 매트릭스 문서가 `docs/reference/`에 커밋됐다(백엔드 브랜치).

## 주의
- 렌더링 확인은 실제 브라우저 기준이다. 코드 리딩만으로 "될 것"이라고 판정하지 않는다.
  확인 불가한 케이스가 생기면 이유와 함께 사람에게 보고한다(통과 위장 금지).
- 설계 갈림길(예: pie·bar 외 chartType을 백엔드가 보낼 수 있게 할지, 프런트에서
  막을지)은 임의로 정하지 말고 P3 질문으로 올린다.

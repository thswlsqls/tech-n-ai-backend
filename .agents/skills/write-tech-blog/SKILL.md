# 기술 블로그 글 작성

주제 하나와 출력 위치를 받아 기술 블로그 글 **한 편**을 쓴다.

이 스킬의 기준 명세는 `docs/reference/writings/001-prompts.md`이고,
실제 글의 톤·구성·인용 방식의 본보기는 `docs/reference/writings/devops/articles/`의 완성 글들이다.
새 글은 그 본보기와 같은 결로 쓴다.

핵심은 "무엇을 쓰는가"가 아니라 **글의 품질 기준을 매번 같은 잣대로 강제하는 절차**다.
특히 AGENTS.md의 두 원칙을 어기지 않는다.

- **외부 자료 참조 원칙**: 기술적 사실은 공식 문서·공식 저장소만 근거로 삼는다. 블로그·포럼·AI 생성 콘텐츠를 근거로 쓰지 않는다.
- **사람이 검증하는 텍스트 작성 규칙**: 상투어·번역투·키워드 나열을 피하고, 읽고 바로 이해되는 줄글로 쓴다.

## 산출물의 정의

완성된 기술 블로그 글 한 편(Markdown 파일)이다. 글은 아래를 갖춘다.

- 본문 제목(H1) + 번호 없는 소제목들
- 글 앞쪽에 **SEO 제목 후보 3개 이상** (각 후보마다 "어떤 검색 의도의 독자를 위한 것인지" 한 줄)
- 줄글 위주의 본문 (목록 나열 남발 금지, 문단을 잘 나눔)
- 글 마지막에 **참고한 공식 문서** 링크 목록
- 분량 **7,000자 이상** (공백 포함 한글 기준)

만들지 않는 것 (= 범위 밖):

- 주제 설계도(아웃라인 문서)만 따로 만드는 일 — 이 스킬은 완성 글 한 편만 낸다. (설계도+글 2단 구조는 `devops/topics`·`devops/articles`의 별도 워크플로다.)
- 여러 편 시리즈 동시 작성 — 한 번에 한 편.
- 공식 문서로 확인되지 않은 수치·기능·버전을 사실처럼 적는 일.

## 인자 해석

사용자 입력에서 다음 셋을 뽑는다. 빠진 게 있으면 묻는다.

- **주제** (필수): 글의 소재. 한 문장으로 좁혀지지 않으면(범위가 너무 넓으면) 후보 각도를 보여주고 어디에 초점을 둘지 묻는다.
- **출력 위치** (필수): 글 파일을 저장할 경로 또는 디렉터리.
  - 파일 경로(`.md`)면 그 이름으로 쓴다.
  - 디렉터리면 주제에서 만든 `kebab-case` 파일명을 붙인다. 그 디렉터리에 번호 접두사 관례(`001-...`)가 있으면 다음 번호를 따른다.
- **1차 소스** (선택): 사용자가 프로젝트 설계 문서 등 1차 소스를 함께 주면, 그 문서에 적힌 사실·수치를 우선 근거로 삼고 공식 문서로 보강한다. 없으면 공식 문서만으로 쓴다.

## 작성 규칙 (001-prompts.md + AGENTS.md)

글을 쓰는 동안 아래 일곱 가지를 지킨다. 이게 이 스킬의 본체다.

1. **톤·문체 — `-ㅂ니다`체로 통일.**
   `devops/articles/`의 완성 글들과 같은 결로 쓴다. 차분하게 설명하는 어조이며, 들뜬 감탄이나 마케팅 문구를 쓰지 않는다.

2. **오만하지 않게.**
   업계 전문가가 읽어도 거슬리지 않도록, 독자를 가르치는 톤을 피한다. 기술적 사실을 적을 때는 "확인된 사실을 정제해 전달한다"는 자세로 쓴다. 단정적인 표현은 가급적 줄이고, 글 끝은 개발자로서 얻은 인사이트를 개인적으로 정리하는 방향으로 맺는다.

3. **공식 문서만 근거로.**
   기술적 사실은 신뢰할 수 있는 공식 기술 문서로만 확인해 쓴다. 필요하면 `WebFetch`/`context7`로 공식 문서를 직접 확인한다. 확인 못 한 내용은 추측해서 적지 말고, 불확실하면 그 점을 글에서 분명히 밝힌다. 논문을 인용할 때는 arXiv/ACM/IEEE/Springer 등 공인 플랫폼 게시본만 쓰고 제목·저자·발행처·URL을 적는다.

4. **LLM 특유의 군더더기 제거.**
   장황한 표현, 방어적인 표현, 억지 논리, 과장된 논리를 걷어낸다. 상투어(`견고한`, `포괄적인`, `원활하게`, `~를 활용하여`, 과한 강조)와 현업에서 안 쓰는 한자어·번역투를 쉬운 말로 바꾼다.

5. **제목·소제목에 번호를 붙이지 않는다.**
   소제목은 적절히 배치하되 `1.`, `2.` 같은 번호는 생략한다.

6. **줄글 위주로 쓴다.**
   목록 나열을 남발하지 않는다. 문단을 잘 나눠 서술형으로 풀어 쓴다. 표나 목록은 줄글로 풀면 더 헷갈릴 때만 제한적으로 쓴다.

7. **SEO 제목 후보 3개 이상.**
   글 앞쪽에 검색 노출을 고려한 제목 후보를 셋 이상 두고, 각 후보가 어떤 검색 의도의 독자를 겨냥하는지 한 줄로 적는다.

분량은 7,000자 이상으로 쓰되, 분량을 채우려고 같은 말을 반복하거나 부풀리지 않는다. 할 말이 모자라면 주제를 한 단계 더 깊이 파고든다.

## 절차

성공 기준은 글 자체가 아래 **검증 체크리스트**를 모두 통과하는 것이다(Goal-Driven Execution).

### 1. 인자 확정 (Think Before Coding)

주제·출력 위치를 확정한다. 주제가 넓거나 출력 위치가 모호하면 멈추고 묻는다. 1차 소스가 있으면 받아 읽는다.

### 2. 근거 수집 (외부 자료 참조 원칙)

글에 들어갈 기술적 사실의 근거를 먼저 모은다.

- 1차 소스가 있으면 거기서 사실·수치를 뽑고, 공식 문서로 교차 확인한다.
- 공식 문서는 `WebFetch`/`context7`로 직접 확인한다. 도구가 없거나 접속이 안 되면, 확인 못 한 사실은 글에 단정적으로 쓰지 않고 그 한계를 글에서 밝힌다.
- 근거가 빈 주장은 적지 않는다. "이 사실은 어느 공식 문서에서 확인했는가"에 답할 수 없으면 빼거나 표현을 누그러뜨린다.

### 3. 글 구성 (Think Before Coding)

본문에 들어가기 전 머릿속으로 흐름을 잡는다. `devops/articles/`의 글 한두 편을 본보기로 톤과 구성을 맞춘다.

- 도입(Hook) → 핵심 질문/맥락 → 본론(소제목별 전개) → 개인적 인사이트로 맺는 마무리 → 참고한 공식 문서
- 이 흐름은 본보기 글에서 반복되는 형태일 뿐 고정 틀은 아니다. 주제에 맞게 조정한다.

### 4. 작성 (작성 규칙 적용)

위 "작성 규칙" 일곱 가지를 지키며 출력 위치에 글을 쓴다. 한 번에 다 쓰고 끝내지 말고, 초안을 쓴 뒤 다음 단계에서 스스로 검수한다.

### 5. 검증 (Goal-Driven Execution)

쓴 글을 아래 체크리스트로 점검한다. 하나라도 어긋나면 고쳐서 다시 점검한다. 통과할 때까지 반복한다.

- [ ] 분량이 7,000자 이상인가 (`wc -m <파일>` 으로 확인)
- [ ] SEO 제목 후보가 3개 이상이고, 각 후보에 검색 의도 한 줄이 붙었는가
- [ ] 소제목에 번호가 없는가
- [ ] 줄글 위주인가 — 목록으로 때운 문단이 없는가
- [ ] 톤이 `-ㅂ니다`체로 일관되고, 가르치는 어조·과한 단정이 없는가
- [ ] 기술적 사실마다 근거가 되는 공식 문서가 있고, 글 끝에 링크가 정리됐는가
- [ ] 상투어·번역투·억지 논리·과장이 없는가 (AGENTS.md "사람이 검증하는 텍스트 작성 규칙")

판단 기준: 글을 그 분야를 모르는 동료에게 소리 내어 읽어준다고 가정한다. 그대로 알아들으면 통과, 단어를 바꿔 설명해야 하면 다시 쓴다.

### 6. 보고

- 한국어로, 사람이 검증하는 텍스트 규칙을 지켜 쓴다.
- 저장한 파일 경로, 글자 수, 사용한 SEO 제목 후보, 근거로 쓴 공식 문서를 짚는다.
- 공식 문서로 확인 못 해 표현을 누그러뜨린 부분이 있으면 그 사실을 알린다.
- 커밋은 하지 않는다. 사용자가 따로 시킬 때만 한다. (커밋 메시지가 필요하면 `commit-message` 스킬을 쓴다.)

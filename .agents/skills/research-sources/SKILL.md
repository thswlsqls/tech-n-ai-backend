# 자료 수집·분석·정리 (공식 출처 우선, 채팅 출력)

주제 하나와 수집 목적을 받아, 그 주제에 필요한 자료를 **공식 출처 위주로 모아 분석하고 정리해서 채팅창에 출력**한다.

이 스킬의 기준은 AGENTS.md의 **외부 자료 참조 원칙**이다.

- 공식 문서·공식 저장소만 1순위 근거로 쓴다. 비공식 블로그·포럼·AI 생성 콘텐츠를 근거로 삼지 않는다.
- 논문은 arXiv/ACM/IEEE/Springer 등 공인 학술 플랫폼 게시본만 쓰고, 제목·저자·발행처·URL을 적는다.
- 확인되지 않은 정보를 사실처럼 제시하지 않는다. 불확실하면 분명히 밝힌다.

핵심은 "무슨 자료를 찾느냐"가 아니라 **출처 등급을 매번 같은 잣대로 강제하고, 확인된 사실과 확인 못 한 내용을 분리하는 절차**다. 이 산출물은 최종물이 아니라 설계·구현·글쓰기로 넘기는 중간 재료다.

## 산출물의 정의

**채팅창에 출력하는 정리물 하나**다. md 파일을 만들지 않는다. 아래 순서로 쓴다.

- **주제와 수집 목적 한 줄** — 무엇을, 무슨 목적(설계/구현/블로그 주제/블로그 본문)으로 조사했는지.
- **핵심 정리** — 주제를 이해하는 데 필요한 사실들을 줄글로 푼다. 각 사실 뒤에 근거 출처를 단다(번호나 링크). 키워드 나열이 아니라 동료가 읽고 바로 이해되는 문장으로.
- **출처 목록** — 참고한 출처를 등급과 함께 적는다. 각 항목에 URL과, 그 출처에서 확인한 내용을 한 줄로.
  - `[공식]` 공식 문서·공식 저장소·공식 릴리스 노트
  - `[논문]` 공인 학술 플랫폼 게시본 (제목·저자·발행처·URL)
  - `[미검증]` 공식으로 확인 못 했으나 참고만 한 자료. 근거가 아님을 명시. 없으면 이 등급은 아예 넣지 않는다.
- **확인 못 한 것 / 상충하는 정보** — 공식 문서로 못 박지 못한 수치·동작, 출처마다 다른 내용. 있으면 솔직히 적는다. 없으면 "없음".
- **목적에 맞춘 활용 포인트** — 수집 목적에 따라 다음 한 묶음만 쓴다(필요한 것만).
  - 설계: 결정해야 할 지점, 트레이드오프, 제약. 공식 문서가 권장/비권장하는 선택.
  - 구현: 건드릴 API·설정·버전 주의점, 함정, 공식 예제 위치.
  - 블로그 주제: 글의 각 후보, 핵심 질문 후보, 근거가 탄탄한 지점 (다음 단계: `plan-blog-topic`).
  - 블로그 본문: 본문에 근거로 박을 사실 묶음과 그 출처 (다음 단계: `write-tech-blog`).

만들지 않는 것 (= 범위 밖):

- 별도 md 파일 — 이 스킬은 채팅 출력만 한다.
- 주제 설계도 — 그건 `plan-blog-topic`.
- 완성 블로그 글 — 그건 `write-tech-blog`.
- 설계 문서·구현 코드 자체 — 이 스킬은 그 앞단의 근거 자료까지만 낸다.
- 공식 문서로 확인 안 된 수치·기능·버전을 근거인 양 적는 일.

## 인자 해석

사용자 입력에서 다음을 뽑는다. 빠진 게 있으면 묻는다.

- **주제·질문** (필수): 조사할 대상. 한 문장으로 좁혀지지 않으면(범위가 너무 넓으면) 좁히는 각을 제안하고 어디에 초점을 둘지 묻는다.
- **수집 목적** (필수): 설계 / 구현 / 블로그 주제 / 블로그 본문 중 무엇을 위한 자료인지. 목적이 "활용 포인트" 절의 모양을 정한다. 안 주면 묻는다.
- **1차 소스** (선택): 사용자가 프로젝트 설계 문서나 특정 공식 URL을 주면, 그 내용을 1순위 근거로 삼고 공식 문서로 보강한다.

## 작성 규칙

- **출처 등급을 먼저 가른다.** 사실을 적기 전에 그 근거가 `[공식]`인지 `[논문]`인지 `[미검증]`인지 정한다. 등급을 못 매기는 자료는 근거로 쓰지 않는다.
- **공식 문서를 직접 확인한다.** `WebSearch`로 공식 출처를 찾고 `WebFetch`/`context7`로 원문을 직접 읽는다. 기억이나 추정으로 수치·버전·동작을 적지 않는다. 도구로 접속이 안 되면, 확인 못 한 사실은 단정하지 말고 "확인 필요"로 남긴다.
- **확인된 사실과 추정을 섞지 않는다.** 공식 문서로 확인한 것만 사실로 적는다. 출처마다 내용이 다르면 "상충하는 정보"에 그대로 드러낸다. 한쪽으로 조용히 정리하지 않는다(Think Before Coding).
- **비공식 자료는 근거로 올리지 않는다.** 블로그·포럼·AI 생성물은 `[미검증]`으로만, 그것도 참고 맥락이 꼭 필요할 때만 적고 근거가 아님을 명시한다. 정 쓸 일이 있으면 같은 사실을 공식 문서로 교차 확인해 `[공식]`으로 올린다.
- **부풀리지 않는다.** 목적에 필요한 만큼만 모은다. 같은 사실을 여러 출처로 중복 나열하지 않는다(필요한 만큼만, 오버엔지니어링 금지).
- **사람이 검증하는 텍스트 작성 규칙을 지킨다.** 상투어·번역투·키워드 나열을 피하고, 비개발자도 알아들을 줄글로 쓴다.

## 절차

성공 기준은 정리물이 아래 **검증 체크리스트**를 모두 통과하는 것이다(Goal-Driven Execution).

### 1. 인자·목적 확정 (Think Before Coding)

주제·수집 목적을 확정한다. 주제가 넓거나 목적이 모호하면 멈추고 묻는다. 1차 소스가 있으면 받아 읽는다. 무엇이 헷갈리는지 짚고 묻되, 가정으로 진행하지 않는다.

### 2. 출처 수집·등급 매기기 (외부 자료 참조 원칙)

주제의 권위 있는 공식 출처가 무엇인지 정한다(해당 기술의 공식 문서, 공식 GitHub 저장소, 공식 릴리스 노트, RFC/표준 문서, 공인 플랫폼 논문). `WebSearch`로 찾고 `WebFetch`/`context7`로 원문을 직접 확인한다. 출처마다 `[공식]`/`[논문]`/`[미검증]` 등급을 매긴다.

### 3. 분석·정리 (산출물의 정의 + 작성 규칙)

확인한 사실을 "핵심 정리"로 줄글로 풀고, 각 사실에 출처를 단다. 공식 문서로 못 박지 못한 것·상충하는 것을 따로 모은다. 수집 목적에 맞는 "활용 포인트" 한 묶음을 쓴다.

### 4. 검증 (Goal-Driven Execution)

정리물을 아래 체크리스트로 점검한다. 하나라도 어긋나면 고쳐서 다시 점검한다.

- [ ] 모든 사실에 출처가 붙고, 출처마다 등급(`[공식]`/`[논문]`/`[미검증]`)이 표시됐는가
- [ ] 근거로 쓴 출처가 공식 문서·공식 저장소·공인 플랫폼 논문뿐인가 (비공식 자료를 근거로 올리지 않았는가)
- [ ] 논문을 인용했다면 제목·저자·발행처·URL을 적었는가
- [ ] 공식 문서로 확인 못 한 내용을 "확인 못 한 것"으로 분리했는가 (사실처럼 단정하지 않았는가)
- [ ] 수집 목적에 맞는 활용 포인트가 들어갔는가 (목적과 무관한 절을 넣지 않았는가)
- [ ] 채팅창에만 출력했는가 (md 파일을 만들지 않았는가)
- [ ] 상투어·번역투·키워드 나열이 없는가 (AGENTS.md "사람이 검증하는 텍스트 작성 규칙")

### 5. 보고

- 한국어로, 사람이 검증하는 텍스트 규칙을 지켜 쓴다.
- 정리물은 채팅창에 그대로 출력한다(파일 저장 금지).
- 공식 문서로 확인 못 해 "확인 필요"로 남긴 부분이 있으면 알린다.
- 다음 단계를 한 줄로 안내한다: 블로그 주제면 `plan-blog-topic`, 완성 글이면 `write-tech-blog`로 넘기면 됨. 설계·구현이면 이 근거를 바탕으로 다음 작업을 이어가면 됨.

# 블로그 단편 주제 설계도 작성

지시자가 준 상세 요구사항을 읽고, 기술 블로그 **단편 한 편**의 주제 설계도(md 파일 1개)를 만든다.

설계도의 본보기는 `docs/reference/writings/devops/topics/`의 단편 파일들이고,
"상세 요구사항 → 주제 기획"의 방식은 `docs/reference/writings/prompts/`의 주제 추출 프롬프트들이 보여준다.
새 설계도는 그 본보기와 같은 결로 쓴다.

이 스킬은 글을 쓰지 않는다. **글을 쓰기 전의 기획 문서**를 만든다.
완성 글로 이어가려면 이 설계도를 `write-tech-blog` 스킬에 1차 소스로 넘긴다.

핵심은 "무슨 주제냐"가 아니라 **설계도가 매번 같은 항목을 같은 잣대로 갖추게 강제하는 절차**다.
특히 AGENTS.md의 두 원칙을 어기지 않는다.

- **외부 자료 참조 원칙**: 기술적 사실의 근거는 공식 문서·공식 저장소만 쓴다. 블로그·포럼·AI 생성 콘텐츠를 근거로 적지 않는다.
- **사람이 검증하는 텍스트 작성 규칙**: 상투어·번역투·키워드 나열을 피하고, 읽고 바로 이해되는 줄글로 쓴다.

## 산출물의 정의

주제 설계도 한 편(Markdown 파일 1개)이다. 아래 항목을 갖춘다(`devops/topics/`의 단편 형식).

- **제목**(H1) — 출력 위치에 번호 접두사 관례(`01-...`)가 있으면 다음 번호를 붙인다.
- **1차 소스** — 지시자가 1차 소스를 줬으면 인용 링크로 박는다. 없으면 생략한다.
- **한줄 요약(Hook)** — 글의 각을 한 문장으로. 인용 블록으로 둔다.
- **핵심 질문** — 글이 답할 질문 2~4개.
- **다루는 관점** — 이 글이 어떤 각도를 다루는지 표시. (devops 본보기는 "설계 근거(Why) / 기본기 / 온프레 비교" 3관점을 쓰지만, 관점은 요구사항에 맞춰 정한다.)
- **근거** — 각 주장의 출처. 1차 소스가 있으면 그 §번호, 없으면 공식 문서로 무엇을 확인할지.
- **타깃 독자 & 난이도** — 독자층 한 줄 + 난이도(★ 5단계) + 필요한 사전지식.
- **예상 분량** — 짧음/보통/김 중 하나 + 대략 글자 수.
- **글 아웃라인** — 도입 → 본론 → 마무리의 절 구성. 기획용이므로 번호를 붙여도 된다(완성 글의 소제목은 `write-tech-blog`에서 번호를 뗀다).
- **참고할 1차 출처** — 글에 쓸 공식 문서 URL 목록.
- **작성 메모** — 글 쓸 때 빠지기 쉬운 함정, 강조점, 톤 메모.

요구사항이 비교 관점(예: 온프레 대비, 다른 기술과의 대조)을 요청하면 **대비 포인트** 절을, 시리즈 맥락이 있으면 **시리즈 인용 관계** 절을 더한다. 없으면 넣지 않는다(필요한 만큼만).

만들지 않는 것 (= 범위 밖):

- 완성된 블로그 글 본문 — 이 스킬은 기획 문서까지만 낸다. (글은 `write-tech-blog`.)
- 여러 단편 + 인덱스 세트 — 한 번에 단편 하나. (시리즈는 `plan-blog-series`.)
- 공식 문서로 확인되지 않은 수치·기능·버전을 근거인 양 적는 일.

## 인자 해석

사용자 입력에서 다음을 뽑는다. 빠진 게 있으면 묻는다.

- **상세 요구사항** (필수): 글이 다뤄야 할 내용. 페르소나, 목표, 꼭 담을 항목, 제약(공식 출처 한정 등)이 섞여 들어올 수 있다(`prompts/`의 추출 프롬프트가 그 예다). 요구사항이 한 편으로 담기엔 너무 넓으면, 좁히는 각을 제안하고 어디에 초점을 둘지 묻는다.
- **출력 위치** (필수): 설계도 md 파일을 저장할 경로 또는 디렉터리.
  - 파일 경로(`.md`)면 그 이름으로 쓴다.
  - 디렉터리면 주제에서 만든 `kebab-case` 파일명을 붙이고, 번호 접두사 관례가 있으면 다음 번호를 따른다.
- **1차 소스** (선택): 프로젝트 설계 문서 등. 주면 그 문서의 §번호·수치를 근거의 1순위로 삼고 공식 문서로 보강한다.

## 작성 규칙

설계도 자체와, 설계도가 지시할 "완성 글의 방향" 모두 아래를 따른다.

- **근거는 공식 문서로.** 설계도의 모든 주장·수치는 1차 소스나 공식 문서로 확인할 수 있어야 한다. 필요하면 `WebFetch`/`context7`로 공식 문서를 직접 확인한다. 확인 못 한 내용은 단정하지 말고, 설계도에 "공식 문서 확인 필요"로 남긴다. 논문은 arXiv/ACM/IEEE/Springer 등 공인 플랫폼 게시본만 쓰고 제목·저자·발행처·URL을 적는다.
- **완성 글의 작성 방향을 미리 못박는다.** 설계도의 아웃라인과 작성 메모는, 나중에 쓸 글이 `write-tech-blog`의 규칙(`-ㅂ니다`체, 가르치지 않는 톤, 번호 없는 소제목, 줄글 위주, SEO 제목 3개+, 개인 인사이트로 마무리)을 지키도록 방향을 잡아 둔다.
- **요구사항을 빠짐없이, 한쪽에 몰지 않게.** 지시자가 "꼭 담을 항목"을 줬으면 아웃라인이 그 항목들을 모두 덮는지 확인한다. 단, 한 편에 다 넣으려다 분량이 터지면 범위를 좁히자고 제안한다(오버엔지니어링 금지).
- **부풀리지 않는다.** 설계도는 글이 아니다. 항목마다 필요한 만큼만 적는다. 작성 메모에 같은 말을 반복하지 않는다.

## 절차

성공 기준은 설계도가 아래 **검증 체크리스트**를 모두 통과하는 것이다(Goal-Driven Execution).

### 1. 요구사항 파악 (Think Before Coding)

상세 요구사항과 출력 위치를 확정한다. 요구사항이 넓거나 출력 위치가 모호하면 멈추고 묻는다. 1차 소스가 있으면 받아 읽는다. 본보기로 `devops/topics/`의 단편 한두 편을 훑어 형식을 맞춘다.

### 2. 근거 점검 (외부 자료 참조 원칙)

아웃라인의 각 절이 어떤 근거 위에 서는지 먼저 정한다. 1차 소스의 §번호 또는 확인할 공식 문서를 짚는다. 근거를 댈 수 없는 절은 아웃라인에서 빼거나 표현을 누그러뜨린다.

### 3. 설계도 작성 (산출물의 정의 + 작성 규칙)

위 "산출물의 정의"의 항목 순서대로 출력 위치에 설계도를 쓴다. 요구사항이 요청하지 않은 절(대비 포인트·시리즈 관계 등)은 넣지 않는다.

### 4. 검증 (Goal-Driven Execution)

쓴 설계도를 아래 체크리스트로 점검한다. 하나라도 어긋나면 고쳐서 다시 점검한다.

- [ ] Hook·핵심 질문·다루는 관점·근거·타깃 독자·예상 분량·글 아웃라인·참고할 1차 출처·작성 메모가 모두 있는가
- [ ] 지시자의 "꼭 담을 항목"을 아웃라인이 빠짐없이 덮는가 (한쪽 절에 몰리지 않았는가)
- [ ] 모든 주장·수치에 1차 소스 §번호 또는 공식 문서 근거가 붙는가 (확인 못 한 건 "확인 필요"로 표시했는가)
- [ ] 참고할 1차 출처가 공식 문서·공식 저장소뿐인가 (블로그·AI 생성물 없음)
- [ ] 아웃라인과 작성 메모가 `write-tech-blog`의 글 작성 방향과 어긋나지 않는가
- [ ] 설계도 텍스트에 상투어·번역투·키워드 나열이 없는가 (AGENTS.md "사람이 검증하는 텍스트 작성 규칙")

### 5. 보고

- 한국어로, 사람이 검증하는 텍스트 규칙을 지켜 쓴다.
- 저장한 파일 경로, 설계도가 잡은 글의 각(Hook), 덮은 요구사항 항목, 근거로 쓸 공식 문서를 짚는다.
- 공식 문서로 확인 못 해 "확인 필요"로 남긴 부분이 있으면 알린다.
- 다음 단계로 `write-tech-blog`에 이 설계도를 넘기면 완성 글을 쓸 수 있음을 한 줄로 안내한다.
- 커밋은 하지 않는다. 사용자가 따로 시킬 때만 한다. (커밋 메시지가 필요하면 `commit-message` 스킬을 쓴다.)

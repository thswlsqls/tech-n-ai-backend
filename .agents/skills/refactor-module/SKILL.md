# 모듈 리팩토링

`tech-n-ai-backend`의 모듈 하나(`api-auth`, `common/core` 등)를 받아 리팩토링한다.

이 스킬의 핵심은 "무엇을 바꾸는가"가 아니라 **AGENTS.md의 4대 행동 지침을 매 단계 강제하는 절차**다.
특히 다음 두 가지를 어기지 않는다.

- **Surgical Changes**: 바뀐 모든 줄은 사용자의 리팩토링 요청으로 곧장 설명돼야 한다. 멀쩡한 인접 코드·주석·포맷은 건드리지 않는다.
- **Goal-Driven Execution**: 리팩토링은 "전후로 테스트가 통과하는지 확인하는" 작업이다. 테스트 그린을 성공 기준으로 삼는다.

## 리팩토링의 정의 (행위 불변)

이 스킬에서 리팩토링은 **겉으로 드러나는 동작을 바꾸지 않고 내부 코드만 다듬는 것**이다.
바꾸는 것:

- 이름: 의도가 드러나지 않는 변수·메서드·클래스 이름
- 함수 크기: 한 가지 일만 하도록 긴 메서드를 쪼갬
- 중복 제거: 같은 로직 반복을 한 곳으로 모음
- 객체지향 설계: 책임이 잘못 놓인 코드를 알맞은 객체로 옮김 (단, 한 번만 쓰는 코드에 억지로 적용하지 않음)

바꾸지 않는 것 (= 리팩토링 범위 밖, 발견하면 보고만 하고 멈춤):

- 외부에서 보이는 동작, 반환값, 예외 종류
- 공개 API 시그니처(컨트롤러 엔드포인트, 다른 모듈이 호출하는 public 메서드)
- DB 스키마, Kafka 이벤트 계약, 엔티티/도큐먼트 필드
- 새 기능·새 추상화·"미래 대비" 코드 (AGENTS.md "오버엔지니어링 금지")

버그를 발견하면 고치지 말고 **별도로 보고한다.** 버그 수정은 리팩토링이 아니라 행위 변경이고, 테스트를 먼저 쓰는 다른 작업이다.

## 모듈 인자 해석

`settings.gradle`은 모듈 이름을 `{parentDir}-{moduleDir}`로 만든다 (`api/auth` → `:api-auth`).
사용자가 어느 표기를 쓰든 받는다.

- `api-auth`, `:api-auth` → Gradle 모듈 `:api-auth`, 경로 `api/auth`
- `api/auth`, `auth` → 같은 모듈로 해석
- 헷갈리면(`source` 처럼 부모가 여럿일 수 있으면) 후보를 보여주고 묻는다.

실제 모듈 목록은 추측하지 말고 확인한다:

```bash
./gradlew projects        # 등록된 모듈 이름
# 또는 디렉터리로
find api batch common client datasource -maxdepth 2 -name src -type d | sed 's|/src||'
```

## 절차

### 1. 모듈 확정과 베이스라인 (Goal-Driven Execution)

먼저 손대기 전에 현재 상태가 그린인지 확인한다. 베이스라인이 깨져 있으면 리팩토링의 전후 비교가 무의미하다.

```bash
./gradlew :<모듈>:clean :<모듈>:build      # 깨끗이 컴파일 + 테스트. 예: ./gradlew :api-auth:clean :api-auth:build
```

베이스라인부터 `clean`을 붙여 낡은 산출물 위에서 그린이 나오는 일을 막는다. 이 레포는 QueryDSL이 `src/main/generated`에 `Q*Entity`를 생성하는데, 증분 빌드는 옛 생성물을 재사용할 수 있어 "사실은 깨졌는데 통과"가 일어난다.

- 그린이면 진행한다.
- 레드면 멈추고 사용자에게 알린다. 내가 만들지 않은 실패를 떠안고 리팩토링하지 않는다.
- 테스트가 아예 없으면 그 사실을 알리고, "리팩토링 후 검증 수단이 컴파일·기존 호출부뿐"이라는 한계를 명시한 뒤 진행 여부를 묻는다.

### 2. 모듈 파악 (Think Before Coding)

모듈의 코드를 읽고 구조를 파악한다. 이 레포의 관례를 머릿속에 둔다.

- CQRS: 쓰기는 Aurora(JPA/QueryDSL, `repository/writer/`), 읽기는 MongoDB/MyBatis(`repository/reader/`)
- 네이밍: Aurora `*Entity`, MongoDB `*Document`, 이력 `*HistoryEntity`
- 의존 방향: `api → datasource → common → client`
- 모듈 안의 기존 스타일을 따른다. 내 취향으로 통일하지 않는다.

읽으면서 리팩토링 후보를 모은다. 각 후보는 "어디가 / 왜 문제인지 / 어떻게 바꿀지 / 행위가 그대로인 근거"가 한 줄로 설명돼야 한다.

### 3. 계획 제시 (사용자 승인)

코드를 바꾸기 전에 후보 목록을 한국어로 정리해 보여주고 **승인을 기다린다.**
해석이 여러 갈래거나 더 단순한 방법이 있으면 조용히 하나만 고르지 말고 모두 제시한다.

각 후보는 이렇게 적는다:

```
- [파일:라인] 현재: <무엇이 문제인가>
  변경: <어떻게 바꾸는가>
  근거: <클린코드/OO 중 무엇 — 행위는 그대로인 이유>
```

부풀리지 않는다. 고칠 게 적으면 적은 대로 보고한다. "고칠 게 거의 없다"도 정직한 결론이다.

### 4. 외과적 적용 (Surgical Changes)

승인받은 후보만 적용한다. 후보 하나 = 변경 하나로 묶어 작게 바꾼다.

- 승인 목록에 없는 변경을 끼워 넣지 않는다.
- 내 변경으로 안 쓰이게 된 import·변수만 제거한다. 기존부터 안 쓰이던 코드는 건드리지 않는다.
- 변경 도중 새 후보가 보이면 적용하지 말고 메모해 뒀다가 마지막에 보고한다.

### 5. 재검증 (Goal-Driven Execution)

**최종 그린 판정은 반드시 `clean build`로 한다.** 증분 빌드는 이전 컴파일 산출물이나 캐시(특히 QueryDSL이 만든 `Q*Entity`)를 재사용해 깨진 변경을 통과시킬 수 있다. 처음부터 다시 컴파일·테스트해야 믿을 수 있다.

```bash
./gradlew :<모듈>:clean :<모듈>:build      # 모듈만 깨끗이 다시 빌드
```

- 그린이면 완료. 변경 요약과 (있다면) 미적용 후보·발견한 버그를 보고한다.
- 레드면 내 변경이 원인이다. 되돌리거나 고쳐서 다시 그린으로 만든다. 레드인 채로 끝내지 않는다.
- 이 모듈을 다른 모듈이 의존하면(예: `common-*`, `datasource-*`) 모듈만 빌드해선 영향이 안 드러난다. 의존 모듈까지 한 번에 보도록 저장소 전체를 깨끗이 다시 빌드한다.

```bash
./gradlew clean build      # 의존 모듈 포함 전체 검증
```

### 6. 보고

- 한국어로, 사람이 검증하는 텍스트 규칙(AGENTS.md)을 지켜 쓴다. 상투어·번역투·키워드 나열을 피한다.
- 무엇을 왜 바꿨는지, 테스트 전후 결과, 미적용으로 남긴 것, 별도로 발견한 버그를 적는다.
- 커밋은 하지 않는다. 사용자가 따로 시킬 때만 한다. (커밋 메시지가 필요하면 `commit-message` 스킬을 쓴다.)

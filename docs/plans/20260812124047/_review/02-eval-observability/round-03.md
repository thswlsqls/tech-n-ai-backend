## 문서에 반영한 수정

### 축 C — 측정 대상의 이름과 해석을 코드에 맞춤

- **표 두 번째 줄 이름을 "개선 여지"에서 "임계값을 통과한 후보 안에서의 상한"으로 바꿨다.**
  이 리스트가 재는 것이 시스템 상한이 아니라 현재 임계값 설정 아래의 상한이라는 점을
  cosine 정규화(`score = (1 + cosine) / 2`)와 함께 적었다.
- **반환값에 `vectorScore`와 `combinedScore`를 둘 다 싣게 했다.** 파이프라인이 `vectorScore`를
  이미 만들어 두므로(`VectorSearchUtil.java:306-307`) 프로젝션에 얹기만 하면 되고, 그러면 같은
  후보 집합으로 벡터 순위 기준 곡선과 융합 순위 기준 곡선을 둘 다 낼 수 있다.
- **"근거 없음" 채점에 전제와 예외 셋을 붙였다.** ① `min-similarity-score > 0`을 전제하며 0이면
  채점 무효 ② fallback 경로에는 판정 지점이 없어 집계에서 제외 ③ 빈 리스트가 "진짜 없음"과
  "조용한 실패" 둘 다를 뜻하므로 검색 경로 값으로 구분. 판정 지점 표현도 "`applyRRF()` 직전"에서
  "하이브리드 벡터 검색 단계가 돌려준 리스트"로 고쳤다.
- **임계값을 0으로 내려 상한을 재는 우회를 명시적으로 금지했다.** `minScore > 0` 가드 때문에
  그 순간 "근거 없음" 채점이 죽는다. 더 넓게 보려면 별도 실행으로 하라고 적었다.
- **두 경로를 섞지 않는 규칙을 넣었다.** fallback 질문은 집계에서 빼고 건수만 보고하며,
  기준선 실행에 fallback이 한 건이라도 나오면 기준선으로 쓰지 않는다.
- **최신성 유형의 처방을 고쳤다.** 두 번째 줄에도 최신성 편향이 남으므로(가중치 0.5 상승 +
  `dateFrom` pre-filter) 벡터 순위 기준 곡선으로만 해석하라고 바꿨다.
- **유형별 최소 건수 규칙을 넣었다.** 유형별 수치를 판정 근거로 쓰려면 10건 이상, 그 아래는
  방향 확인용. 전체 최소 30건은 그대로 두고 100건으로 늘릴 때의 우선순위를 적었다.
- **기준선 재측정에 선행 조건 둘을 붙였다.** 03·04가 기존 검색 경로를 설정으로 끌 수 있게 남길
  것, 다시 재기 전에 기대 근거의 존재와 `status`를 전수 재확인할 것.
- **(c)의 판정 축과 산출 형식을 정의했다.** 근거 기반성·질문 응답성 두 축, 0/1 이진 판정,
  집계는 축별 통과 비율과 건수. 척도를 안 쓰는 이유도 적었다.
- ANN 근사 오차와 `exact = true` 선택지, 최신성 쿼리의 중복 미제거를 각각 한 줄씩 남겼다.

### 축 D — 실행을 막는 것들

- **9항목을 10항목으로 늘렸다. 새로 넣은 것이 "설정 브리지 클래스"다.**
  `@Profile`이 등록 장치가 아니라 필터라는 점을 명시하고, `batch/source`의 `ServerConfig`를
  본뜨라고 적었다. 이게 없으면 문서대로 만들어도 `batchMetaDataSource`를 못 찾아 안 뜬다.
- **0단계를 0a·0b로 쪼갰다.** 0a는 `./gradlew :batch-eval:dependencies --configuration
  runtimeClasspath`로 클래스패스만 확인한다 — DB도 API 키도 필요 없고 `jar.enabled` 질문에만
  답한다. 0b는 브리지와 프로필까지 넣은 뒤 띄우고, 통과 조건을 관측 가능한 문장으로 적었다.
  **빈 관련 실패는 `jar.enabled`와 무관하다는 구분 기준도 넣었다** — 이게 없으면 전혀 다른
  원인의 실행 실패가 "공용 모듈로 빼는 설계 변경"으로 오진된다.
- **JobRepository 세 선택지의 대가를 나란히 적었다.** 기존 스키마 공유의 대가(DataSource 3개·
  EMF 2개·MyBatis 2세트), 새 스키마의 DDL 문제, 그리고 `ResourcelessJobRepository`·
  `MongoJobRepositoryFactoryBean`을 고르면 네 항목이 통째로 사라진다는 점.
- **`@Import` 최소 집합에 `MongoClientConfig`를 넣었다.** 빼도 Boot가 기본 `MongoTemplate`을
  만들어 실행은 되지만 운영과 다른 클라이언트로 재게 된다는 이유를 붙였다.
- **완료 기준을 11개에서 14개로 늘리고 각 항목에 판정 방법을 괄호로 붙였다.** 새로 넣은 셋은
  0a 클래스패스 확인, 검색 옵션 조립 분리, temperature 0 실행 확인이다. 5번·6번의 모순은
  리포트를 "공통 필드 + 잡별 필드"로 나눠 풀고 6번을 "공통 필드가 같다"로 고쳤다.
  판정 주체와 시점("각 작업의 PR 리뷰에서, 증거는 PR 본문에")도 적었다.
- **리포트 출력 경로를 잡 파라미터·프로퍼티로 받게 했다.** 작업 디렉터리가 모듈 폴더라서
  루트 기준 상대경로가 그대로는 안 맞는다.
- temperature 0 고정이 `chatbot-api` 프로필과 충돌한다는 점을 (c)와 프로필 충돌 처리 양쪽에
  적었다. `module.mysql.port`와 같은 자리에서 같은 방식으로 처리한다.

## 반영하지 않은 지적과 이유

- **분량 압축이 이번에도 실패했다.** 위원 E가 −82행(465 → 383행) 압축안을 줄 번호 범위까지
  지정해 냈고 그중 표현·중복 항목은 반영했다. 그러나 축 C·D 수정이 요구한 서술이 그보다 커서
  **결과는 465행 → 530행이다.** 압축 후 다시 세 군데를 더 줄여 541에서 530으로 내렸지만,
  검증된 사실을 버리지 않는 선에서는 여기가 한계였다. 위원 E 본인도 "더 줄이려면 검증된
  사실을 버려야 하고, 그건 E축이 A~D축 점수를 깎는 거래"라고 적었다.
- **`batch/eval` 요건을 별도 파일로 빼는 안(−33행 이상).** 위원 E가 가장 큰 단일 절감으로
  권했으나, impl 파이프라인이 계획 문서 외의 파일을 읽는지 확인하지 못했다. 구조를 바꾸는
  결정이고 전제가 미확인이라 이번에는 하지 않는다. **라운드 4의 결정 사항으로 넘긴다.**
- **위원 C의 nDCG·MAP.** 라운드 1·2와 같은 이유로 세 번째도 받지 않았다 (이번에는 아예
  프롬프트에서 제안하지 말라고 지시했다).
- **위원 A의 (e) 범위 조정 중 "지연 축을 이 단계에서 완결".** 선행 조건은 좁혔지만 (e) 자체를
  앞당기지는 않았다. 운영 배포가 걸린 일이라 오프라인 평가와 성격이 다르다는 기존 판단을
  유지한다.
- **05-backlog 쪽 서술 수정.** 02가 오프라인 토큰 집계를 맡기로 하면서 순환 참조는 풀렸지만,
  05 문서의 세 곳(`:62`, `:162`, `:187`)이 아직 02를 비용 측정의 주인으로 적고 있다.
  이 평가의 범위는 02 문서라 남겨 둔다.
- **`jar.enabled = true`의 Gradle 차원 확정.** 라운드 2와 같이 fat jar 내용물이라는 간접 증거로
  판단했다. 이번에는 확정 명령을 0a로 문서에 넣었으므로 구현 첫 단계에서 답이 나온다.
- **Atlas 인덱스 filter 등록 여부.** 세 라운드 연속 확인 불가. 리스크 절의 행동 항목 유지.
- **임계값 0.7이 실제로 정답을 얼마나 자르는지, 한국어 질문 대 영어 문서 임베딩 문제.**
  위원 C가 미확인 우려로 올렸다. Atlas 접속 없이는 확인할 수 없다. 사실이면 C-1의 임계값
  문제가 크게 커지므로 골든셋을 만들면서 함께 본다.

## 문서에 반영한 수정

### 축 A
- **A-1** "이 숫자들이 왜 이 값인지 설명할 근거가 저장소에 없다" → "근거는 설계 문서 005에
  있고, 없는 것은 실측이다"로 고쳤다. 참고 절에 설계 문서를 추가했다.
- **A-3** (e)가 (a)~(d)와 성격이 다르다는 점(오프라인 평가 vs 운영 코드 배포)을 (e) 절 끝에
  명시했다.
- **A-4** 토큰·비용 작업을 05로 빼면 비용 축의 주인이 없어진다는 점을 "제외" 절에 적었다.
  04단계 판정 기준이 비용을 요구한다는 사실과 함께.

### 축 B
- **B-1** "1.18.x 라인에만 있다" → "1.12.1-beta21부터 있고, 01단계가 검토 중인 1.13.x로도
  (e)가 가능하다"로 고쳤다. 이 오류는 01단계의 버전 선택 판단을 왜곡할 수 있었다.
- **B-2** Prometheus 스크레이프 잡 서술을 실제 대상(`spring-boot-api`)만 짚도록 좁혔다.

### 축 C
- **C1** (가장 무거운 결함) 측정 지점과 k를 정의했다. 잘림이 세 군데라 체인 끝에서는 k>5를
  잴 수 없다는 사실을 적고, 같은 골든셋을 `max-search-results` 5(운영 재현)와 50(개선 여지)
  으로 두 번 돌리는 방식을 표로 넣었다. 두 실행의 파이프라인 차이(`searchLimit = maxResults*3`)
  와 `numCandidates` 200/150이면 k=50까지 후보가 충분하다는 점도 적었다.
- **C2** "근거 없음" 유형을 recall·MRR 집계에서 빼고 `min-similarity-score` 초과 결과 유무로
  채점하도록 바꿨다. 최신성 쿼리에 유사도 임계값이 없어 어떤 질문에도 문서 3~5건이 항상
  붙는다는 사실을 근거로 적었다.
- **C3** 판정 기준에 표본 크기 항목을 넣었다. n=30에서 ±0.17 신뢰구간, 짝지은 비교와
  개선/악화 항목 수 기록.
- **C4** 골든셋 유형을 체인이 실제로 보는 축(provider, update_type, 최신성 키워드)에 맞춰
  다시 나눴다. "종류 한정"을 추가하고, "기간 한정"을 "최신성 키워드"로 바꾸면서 날짜 지정
  질문을 여기 넣으면 안 되는 이유를 적었다.
- **C5** 평가 실행에서 temperature 0 고정을 요구하고, 지금은 리터럴이라 코드 수정이 필요하다는
  사실을 적었다.
- **C6** "비교 시점에 기준선을 다시 잰다"를 판정 기준에 넣었다. 기록만으로는 원인을 나눌 수
  없기 때문이다.
- **C7** `PromptService`가 잘린 근거 목록을 함께 반환하도록 고치는 쪽으로 확정했다. 평가
  모듈에서 자르기를 다시 구현하면 로직이 갈라진다.
- **C8** 임베딩 캐시 키에 모델 이름과 차원을 넣도록 했다.

### 축 D
- **D-1** `batch/eval` 신설에 실제로 필요한 것을 다섯 항목으로 풀어 적었다 — `:api-chatbot`
  의존 추가, `application.yml`/`application-local.yml` 구성, JobRepository 스키마 결정,
  `@Import`로 필요한 빈만 올리기, `implementation` 전파 문제.
- **D-2** (e)에 대응하는 완료 기준을 추가하고, 미터를 어느 모듈에 넣는지 적었다
  (LLM·검색은 `api-chatbot`, 툴 호출은 `api-agent`).
- **D-3** 검색 경로를 리포트에 남기려면 `api-chatbot` 수정이 필요하다는 점을 범위 포함에
  명시하고, 진행 순서 2단계로 넣었다.
- **D-4** 열린 질문 1(골든셋 위치)과 4(모듈 위치)를 제거하고 확정 근거를 적었다. 판단에
  필요한 사실이 문서 안에 이미 다 있어 P3로 올릴 이유가 없다.
- **D-5** impl input 파일명을 타임스탬프 형식으로 바꾸고, 형제 문서들의 순번이 겹친다는 점을
  적었다.
- **D-6** 환경변수 두 개를 이름으로 적고, 비어 있으면 잡이 즉시 멈추도록 요구했다.
- **D-7** 완료 기준 7을 판정 가능하게 다시 썼다. 커버리지 도구가 없으므로 채점 로직 세 가지에
  대한 단위 테스트 존재 여부로 판정한다.

## 반영하지 않은 지적과 이유

- **위원 A: README 순서 서술 어긋남.** `README.md:67-72`가 "01은 나머지 전부의 선행 조건"이라
  못박는데, 02 문서는 (a)~(d)를 01보다 먼저 해도 된다고 적는다. 확인해 보니 **02 쪽이
  정확하다** — 01이 필요한 것은 (e)뿐이다. 고칠 대상은 README이고 이번 평가 범위 밖이라
  건드리지 않았다. 별도 작업으로 남긴다.
- **위원 C: nDCG·MAP 추가.** 기대 근거가 질문당 소수이고 이진 판정이라 MRR·recall로 충분하다는
  위원 C 본인의 판단을 따랐다.
- **위원 C·D: `api-chatbot`을 라이브러리로 쓸 수 있는지.** 실제 빌드로 확인해야 하는 사항이라
  문서에는 "모듈을 만들자마자 이것부터 확인한다"는 리스크로만 남겼다.
- **위원 C: Atlas 인덱스에 `update_type`·`published_at`이 filter로 등록됐는지.** Atlas 쪽을
  확인할 수 없어 미확인으로 둔다. 등록이 안 돼 있으면 pre-filter가 조용히 실패한다.
- **위원 E의 일부 표현 지적** 중 원문의 담백한 문체를 해치는 제안은 받지 않았다.

## 다음 라운드가 중점적으로 볼 것

1. **C1의 해법이 실제로 성립하는가.** `max-search-results`를 50으로 올린 실행이 정말 같은
   파이프라인을 재는지, `searchLimit`과 RRF 자르기 깊이 변화가 수치를 왜곡하지 않는지.
2. **범위가 커졌다.** `api-chatbot` 수정 세 가지(검색 경로 반환, `PromptService` 반환 확장,
   temperature 설정화)를 이 단계에 넣었다. 오버엔지니어링 금지 기준에서 이게 정당한지,
   아니면 단계를 쪼개야 하는지.
3. **D-1의 다섯 항목이 빠짐없는가.** 실제로 `batch/eval`을 만들 때 또 막히는 것이 없는지.
4. **새로 넣은 서술의 사실 정확성.** 이번 수정에서 인용한 줄 번호와 설정 키가 맞는지 다시
   전수 대조.
5. **문서가 길어졌다.** E축 기준으로 늘어난 분량이 정당한지, 압축할 곳이 없는지.

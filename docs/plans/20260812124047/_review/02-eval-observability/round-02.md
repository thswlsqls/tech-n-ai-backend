## 취합자가 직접 재확인한 것

에이전트 보고를 그대로 믿고 문서를 고치면 안 되므로, 문서 수정의 근거가 되는 지적은 전부
직접 확인했다. 여덟 건 다 사실이었다.

| 지적 | 확인 방법과 결과 |
|------|------------------|
| "근거 없음" 채점이 성립 불가 | `applyRRF()`가 `.score()`를 RRF 점수로 덮어씀(`VectorSearchServiceImpl.java:311-321`). 최댓값 `1.5/61 = 0.0246` — 0.7을 원리적으로 못 넘는다. 반대로 fallback 경로(`:365-368` 직전)는 전건이 `$match(score >= 0.7)` 통과분이라 전건 초과. **같은 규칙이 경로에 따라 정반대 답을 낸다** |
| 최신성 5건이 벡터 전부를 앞섬 | 검산: 최신성 rank4 `1.5/65 = 0.02308` > 벡터 rank0 `1.0/61 = 0.01639`. 비감지도 가중치 1.0으로 동점 인터리브 |
| k=50 실행의 후보 배수 | `searchLimit = maxResults*3`(`:105`), `numCandidates` 상수 150(`:109`) → k=5는 10배, k=50은 **1.0배**, k=51은 `limit`(153) > `numCandidates`(150). MongoDB 공식 문서에서 "20배 이상 권고"와 HNSW 큐 크기 설명 확인 |
| `PromptService` 수정이 불필요 | `TokenService.truncateResults(List<SearchResult>, int)`가 인터페이스에 공개돼 있음. 위원 A와 C의 판단이 엇갈렸고 **A가 맞았다** — C는 `buildPrompt()` 호출처만 세고 더 싼 경로를 못 봤다 |
| temperature가 죽은 설정 키 | `application-chatbot-api.yml:12`에 `langchain4j.open-ai.chat-model.temperature: 0.7`이 있는데 `LangChain4jConfig`(`:25-38`)에 이를 읽는 `@Value`가 없다. 키 신설이 아니라 연결 작업 |
| 임베딩 캐시 키 이름 오류 | 실제는 `langchain4j.open-ai.embedding-model.model-name`/`.dimensions`(`LangChain4jConfig.java:34,37`). `chatbot.embedding-model.*`는 저장소에 없음 |
| `jar.enabled = false` 전파 실패 | **실증.** `batch/source/build/libs/batch-source-0.0.1-SNAPSHOT.jar`의 `BOOT-INF/lib`에 `common-*`·`datasource-*`·`client-*`가 전부 `-plain.jar`로 있는데 `api-emerging-tech`만 없고, `api/emergingtech` 클래스 엔트리 0건. 문서가 안심 근거로 든 전례가 반증 사례였다 |
| `batch/eval` 요건 누락 | `batch/source` 실물 대조: `BatchConfig.java:7-12`(`@EnableBatchProcessing` + `@EnableJdbcJobRepository`), `BatchSourceApplication.java:6-9`(DataSource autoconfig 제외), `application.yml:4-17`의 `batch-domain` 프로필, `application-chatbot-api.yml:4-5`의 `module.mysql.port: 3310` 덮어쓰기, `spring.batch.jdbc.initialize-schema` 부재, `ResultRefinementChain.java:24`의 `ReRankingService` 필수 의존 |

외부 사실도 확인했다. `langchain4j-observation`과 `langchain4j-micrometer-metrics`의 버전
목록은 17개로 **완전히 동일**하고 `1.13.0-beta23`·`1.13.1-beta23`이 실재한다 — 문서 서술이
맞아 감점 없음.

## 문서에 반영한 수정

### 축 C — 측정 방식 전면 교체 (가장 큰 변경)

- **"두 번 돌리기"를 삭제하고 왜 쓰지 않는지를 적었다.** 후보 배수 10배→1.0배, k=51 이상에서
  하이브리드 실패, 하이브리드가 `SearchOptions.numCandidates()`를 무시하는 점, 최신성 건수가
  상수인 점, `ResultRefinementChain`만 프로퍼티를 직접 읽어 한 잡에서 두 k를 못 도는 점.
- **대신 `applyRRF()` 직전의 원시 후보 리스트를 반환값에 실어 재도록 바꿨다.** 운영 설정을
  건드리지 않아 파이프라인이 그대로이고, k를 1~15로 잡아 recall@k 곡선을 그릴 수 있고, 잡도
  한 번만 돈다. 15건이 모자라면 그때 `numCandidates`와 `searchLimit`을 함께 넓히라고 적었다.
- **"근거 없음" 채점을 원시 벡터 후보가 비었는지로 바꿨다.** 반환 `score`로는 못 한다는 이유를
  숫자와 함께 적었다.
- **최신성 유형 해석 주의를 새로 넣었다.** RRF 가중치 1.5 때문에 이 유형의 k=5 수치는 검색
  품질이 아니라 "최신 5건 적중률"이라는 점.
- **검색 옵션 조립을 별도 컴포넌트로 빼라고 (b)에 명시했다.**

### 축 D

  답변 품질용(5단계)으로 쪼갰다. 6단계 끝에 답변 품질 기준선 기록을 넣었다.

## 다음 라운드가 중점적으로 볼 것

1. **원시 후보 반환 방식이 정말 성립하는가.** 이번에 "두 번 돌리기"를 대체한 장치다. 라운드 1의
   교훈이 여기 그대로 적용된다 — 해법을 넣을 때마다 새 결함이 딸려 왔다. `VectorSearchService`
   반환 타입을 바꿀 때 파급, 벡터 후보 15건이 03단계 판정에 충분한지, `$match(vectorScore)`가
   이미 걸린 리스트로 recall@k를 재는 것이 무엇을 재는 것인지.
2. **`batch/eval` 요건이 이제 빠짐없는가.** 5항목에서 9항목이 됐다. 그래도 또 막히는 것이 있는지,
   특히 `@Import` 최소 집합과 MongoTemplate·Mongo 컨버터 설정.
3. **분량.** 466행으로 형제 문서(154~196행)의 2.4~3배가 됐다. E축 기준으로 어디를 줄일지
   구체 안을 받아 이번에는 실제로 줄인다. 특히 "왜 이 단계인가" 절과 (b) 절의 재배치.
4. **이번에 새로 인용한 줄 번호·설정 키의 전수 대조.** 라운드 1에서 인용을 고치다 새 오류가
   생겼고(`:971`, `chatbot.embedding-model.*`) 이번에도 인용이 크게 늘었다.
5. **A축의 범위 판단.** `PromptService`를 뺐지만 `buildSearchOptions` 분리와
   `jar.enabled = true`가 새로 들어와 운영 코드를 건드리는 항목이 여전히 넷이다
   (반환값 확장, 옵션 조립 분리, `jar.enabled`, temperature 연결). 오버엔지니어링 금지 기준에서
   이 넷이 각각 정당한지 다시 본다.

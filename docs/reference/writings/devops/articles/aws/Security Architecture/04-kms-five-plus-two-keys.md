## 들어가며

세 환경의 보안 다이어그램을 나란히 놓고 가운데 "KMS(encryption keys)" 상자만 들여다보면, 초록 열쇠 아이콘이 일곱 개 그려져 있습니다. 위쪽 두 개(`tfstate`, `ecr`)에는 "bootstrap(shared, env-agnostic)"이라는 라벨이 붙어 세 환경이 함께 쓴다고 적혀 있고, 아래쪽 다섯 개(`{env}-data`, `{env}-s3-app`, `{env}-auth`, `{env}-ai`, `{env}-logs`)는 dev·beta·prod마다 따로 만들어집니다. 계정 하나에 데이터를 암호화하는 키 하나면 충분해 보이는데, 왜 아래쪽 다섯 개는 용도별로 쪼개 두었을까요.

이 프로젝트의 `architecture-facts.md`가 기록한 KMS 키 목록을 세어 보면, bootstrap 공유 2개에 환경별 5개씩 세 환경(dev 5, beta 5, prod 5)을 더해서 모두 열일곱 개입니다. 다이어그램 한 장에 그려진 일곱 개는 그중 한 환경(prod) 몫에 공유 두 개를 얹은 그림입니다. 이 글에서는 이 "5 + 2" 구조가 어떤 원칙 위에 서 있는지, 그리고 그 원칙이 감수하는 비용은 무엇인지를 AWS 공식 문서와 이 저장소의 Terraform 설정을 근거로 짚어 보려 합니다. 결론을 먼저 말하면, 키를 쪼갠 기준은 "암호화 성능"이 아니라 "누가 무엇을 복호화할 수 있는가라는 접근 경계를 어디에 그을 것인가"였습니다.

## 봉투 암호화 — 키 하나로 다 감싸면 안 되는 이유

먼저 KMS 키가 실제로 무엇을 하는지부터 정리해야 이야기가 됩니다. 흔히 "KMS 키로 데이터를 암호화한다"고 말하지만, AWS 공식 문서는 KMS 키가 데이터를 직접 암호화하는 일은 거의 없다고 설명합니다. KMS 키는 대부분 **래핑 키(wrapping key), 다른 말로 키를 암호화하는 키(key-encryption key)**로 쓰입니다. 실제 데이터는 데이터 키(data key)가 암호화하고, KMS 키는 그 데이터 키를 감싸는 역할만 합니다. 이 구조를 봉투 암호화(envelope encryption)라고 부릅니다.

흐름을 풀어 보면 이렇습니다. 어떤 서비스가 데이터를 암호화하려 할 때 KMS에 데이터 키를 하나 요청하면, KMS는 평문 데이터 키와 그 데이터 키를 KMS 키로 암호화한 암호문 데이터 키를 함께 돌려줍니다. 서비스는 평문 데이터 키로 데이터를 암호화한 뒤 평문 키는 메모리에서 버리고, 암호문 데이터 키만 데이터 옆에 같이 저장합니다. 나중에 복호화가 필요하면 저장해 둔 암호문 데이터 키를 KMS로 보내고, KMS가 자신이 보관한 KMS 키로 그것을 풀어 평문 데이터 키를 돌려주면, 그제서야 데이터를 복호화할 수 있습니다. KMS 키의 핵심 재료는 KMS의 HSM 밖으로 평문 상태로 나오지 않도록 설계돼 있어서, 이 마지막 단계는 반드시 KMS를 한 번 거쳐야만 성립합니다.

여기서 중요한 사실이 하나 드러납니다. 데이터를 복호화할 수 있느냐 없느냐는 결국 "그 데이터 키를 감싼 KMS 키로 Decrypt를 호출할 권한이 있느냐"로 결정된다는 점입니다. 그리고 그 권한은 KMS 키마다 붙는 키 정책(key policy)과 IAM 정책, grant로 정해집니다. AWS 문서는 고객이 만든 KMS 키(customer managed key)에 대해 키 정책·IAM 정책·grant를 직접 세우고 관리한다고 명시하는데, 이 저장소의 열일곱 개 키가 모두 여기에 해당합니다. Terraform으로 `aws_kms_key`를 선언해 만든 키이기 때문입니다.

이제 "키 하나로 다 감싸면 안 되는 이유"가 보입니다. 만약 한 환경의 모든 데이터 키를 KMS 키 하나로 감싸 두면, 그 키에 Decrypt 권한을 얻은 주체는 그 환경의 모든 데이터를 풀 수 있습니다. 데이터베이스도, 애플리케이션이 올린 파일도, JWT 서명 키도, 외부 API 키도, 로그도 전부 같은 열쇠 하나에 걸려 있는 셈입니다. 어떤 서비스나 자격 증명 하나가 잘못 넓은 권한을 갖게 되거나 유출되면, 피해가 그 키가 감싼 모든 것으로 번집니다. 보안에서 이 "한 번의 사고가 영향을 미치는 범위"를 흔히 폭발 반경(blast radius)이라고 부릅니다. 키를 용도별로 쪼갠다는 것은, 하나가 뚫렸을 때 함께 뚫리는 범위를 그 용도 안으로 가둬 두겠다는 결정입니다. 봉투 암호화 자체가 이 격리를 강제하지는 않습니다. 격리는 "데이터 키를 어느 KMS 키로 감쌀 것인가"를 나눠 정하고, 그 키마다 접근 정책을 따로 붙일 때 비로소 생깁니다.

## 다섯 개로 쪼갠 경계 읽기

그렇다면 이 프로젝트는 환경마다 다섯 개의 경계를 어디에 그었을까요. `architecture-facts.md` §5가 기록한 각 키의 보호 대상을 줄로 풀면 이렇습니다.

`{env}-data`는 데이터 저장소의 데이터를 감쌉니다. Aurora MySQL, MongoDB, ElastiCache(Valkey), MSK가 여기에 묶입니다. 서비스가 상태를 읽고 쓰는 1차 저장소 계층입니다. `{env}-s3-app`은 애플리케이션이 다루는 S3를 따로 감쌉니다. 같은 "저장소"라도 객체 스토리지는 접근 주체와 사용 방식이 데이터베이스와 다르기 때문에 경계를 분리해 둔 것으로 읽힙니다. `{env}-auth`는 인증에 쓰이는 비밀을 감쌉니다. JWT 서명 키와 RDS IAM 인증을 위한 봉투가 여기에 들어갑니다. `{env}-ai`는 OpenAI·Cohere 같은 외부 LLM 제공자의 API 키를 감쌉니다. `{env}-logs`는 CloudWatch Logs와 Athena 쪽 로그 데이터를 감싸며, CloudWatch Logs 서비스가 이 키를 쓸 수 있도록 서비스용 키 정책이 함께 붙어 있습니다.

이 다섯을 나란히 놓고 보면, 경계를 가른 기준이 "데이터의 종류"가 아니라 "이 데이터에 접근하는 주체와 상황의 조합"이라는 게 드러납니다. 데이터 저장소를 읽는 서비스, S3에 파일을 올리는 서비스, 토큰을 서명하는 인증 경로, 외부 AI API를 호출하는 서비스, 로그를 쌓는 관측 파이프라인은 서로 다른 주체이고, 각자가 필요로 하는 복호화 권한도 다릅니다. 예를 들어 로그 파이프라인이 데이터베이스 데이터 키를 풀 이유는 없고, 외부 AI 키를 다루는 서비스가 JWT 서명 키를 풀 이유도 없습니다. 키를 이렇게 나눠 두면 각 키의 정책에 "이 키는 이 용도의 주체만 쓴다"는 최소 권한을 붙일 수 있고, 한 축이 무너져도 다른 축의 데이터는 다른 열쇠 뒤에 그대로 남습니다.

한 가지는 정직하게 구분해 두려 합니다. 다이어그램 오른쪽 범례는 각 키가 보호하는 대상을 조금 더 세밀하게(예: 특정 시크릿 이름 단위로) 적어 두고 있는데, `architecture-facts.md`의 IAM 기록과 대조해 보면 개별 시크릿이 정확히 어느 키에 걸려 있는지에 대해서는 문서 사이에 결이 다른 부분이 있습니다. 그래서 이 글에서는 §5 KMS 기록이 명확히 밝힌 "키별 용도 경계" 수준까지만 단정하고, 시크릿 하나하나가 어느 키로 감싸졌는지는 코드로 더 확인해야 할 영역으로 남겨 둡니다. 경계를 다섯 갈래로 나눈 큰 틀 자체는 두 문서가 일치합니다.

## bootstrap 두 개만 세 환경이 공유하는 이유

아래쪽 다섯 개가 환경마다 새로 만들어지는 것과 달리, 위쪽 두 개(`tfstate`, `ecr`)는 세 환경이 함께 씁니다. 이 차이도 원칙에서 나옵니다.

`tfstate` 키는 Terraform 상태 파일을 담는 S3와 잠금(lock)에 쓰는 DynamoDB를 암호화합니다. `ecr` 키는 컨테이너 이미지 레이어가 올라가는 ECR을 암호화합니다. 두 대상 모두 "특정 환경에 속한 데이터"가 아니라 "그 환경들을 만들어 내는 데 쓰이는 재료"라는 공통점이 있습니다. Terraform 상태는 dev·beta·prod를 각각 어떤 모습으로 배포했는지를 기록하는 메타데이터이고, ECR 이미지는 세 환경이 같은 아티팩트를 가져다 배포하는 원본입니다. 이들은 환경보다 한 층 위, 환경을 정의하고 공급하는 부트스트랩 계층에 있습니다. 그래서 환경별로 쪼개는 대신 부트스트랩에서 한 번만 만들어 공유하는 편이 개념에 맞습니다. 환경마다 상태 저장 키를 따로 두는 것은, 오히려 "환경보다 상위인 것을 환경 아래로 끌어내리는" 어색한 구조가 됩니다.

정리하면 이 저장소의 키 구조는 두 가지 다른 축을 동시에 표현하고 있습니다. 세로축은 용도(데이터·S3·인증·AI·로그)이고, 가로축은 소속(특정 환경에 속하는가, 아니면 환경들을 만드는 부트스트랩에 속하는가)입니다. 부트스트랩 계층은 소속이 환경보다 위라 공유되고, 워크로드 계층은 환경별로 격리됩니다. 열일곱이라는 숫자는 이 두 축이 곱해진 결과입니다.

## rotation on과 deletion window 30d는 서로 다른 스위치다

다이어그램의 키 상자에는 "rotation on · 30d window"라는 라벨이 붙어 있습니다. 얼핏 보면 "30일마다 순환한다"처럼 읽히기 쉽지만, 이 두 값은 완전히 다른 설정이고 서로 상관이 없습니다. `architecture-facts.md`도 "rotation 모두 on"(자동 순환 활성화)과 "deletion window 30d"(키 삭제 시 대기 기간)를 별개 사실로 나눠 적고 있습니다. 둘을 구분해 두는 편이 정확합니다.

자동 순환(automatic key rotation)은 KMS 키의 암호화 재료를 주기적으로 새로 만드는 기능입니다. AWS 문서에 따르면 이 기능을 켜면 기본값으로 1년에 한 번 새 키 재료가 생성되고, 원하면 순환 주기(rotation period)를 일 단위로 따로 지정할 수도 있습니다. 여기서 눈여겨볼 점은, 순환이 바꾸는 것은 "현재 사용하는 키 재료"뿐이고 KMS 키 자체는 같은 논리적 자원으로 남는다는 사실입니다. 키 ID도 그대로이고, 이전 재료도 보관돼 있어서 예전에 그 재료로 암호화한 데이터는 계속 복호화됩니다. KMS가 복호화할 때 어떤 재료로 암호화됐는지 알아서 골라 주기 때문에, 순환이 일어나도 애플리케이션 코드를 바꿀 필요가 없습니다. 다만 문서는 분명히 선을 긋습니다. 키 순환은 이미 암호화된 데이터를 다시 암호화하지 않고, 이미 만들어진 데이터 키를 순환시키지도 않으며, 유출된 데이터 키의 피해를 되돌려 주지도 않습니다. 순환은 "장기적으로 같은 재료를 지나치게 오래 재사용하지 않게 한다" 정도의 위생 관리이지, 사고 대응 수단이 아닙니다.

반대로 삭제 대기 기간(deletion window)은 순환과 아무 관계가 없는, 삭제에 관한 안전장치입니다. AWS 문서는 KMS 키를 삭제하는 일이 되돌릴 수 없고 위험하기 때문에 삭제를 예약할 때 7일에서 30일 사이의 대기 기간을 반드시 두도록 강제한다고 설명합니다. 기본값이 30일입니다. 이 저장소가 잡아 둔 "deletion window 30d"는 바로 이 값을 최대치로 설정해 둔 것입니다. 대기 기간 동안 키는 "삭제 대기(Pending deletion)" 상태가 되어 어떤 암호화·복호화 연산에도 쓰이지 못하지만, 그 사이에 예약을 취소하면 키를 되살릴 수 있습니다. 일단 실제로 삭제되면 그 키로 암호화한 데이터는 영영 복구할 수 없습니다. 그래서 30일이라는 넉넉한 창은 "실수로, 혹은 성급하게 지운 키를 되돌릴 시간을 최대한 벌어 둔다"는 뜻입니다.

두 값을 이렇게 갈라 놓고 보면 라벨이 다르게 읽힙니다. "rotation on"은 키 재료를 주기적으로 갈아 준다는 운영 상태이고, "30d window"는 이 키를 지우려 할 때 30일을 기다리게 만든다는 삭제 방어선입니다. 하나는 살아 있는 키의 위생, 다른 하나는 키를 죽일 때의 브레이크입니다. 열일곱 개 키 모두 이 두 설정을 켜 두었다는 것은, 각 키를 오래 안전하게 유지하는 쪽과 실수로 잃지 않는 쪽을 동시에 챙겼다는 의미로 읽었습니다.

## 마치며 — 쪼개는 관리 비용과, 좁혀 둔 피해 범위

키를 용도별·환경별로 쪼개는 결정에는 분명한 비용이 따릅니다. 고객이 만든 KMS 키는 존재하는 것만으로 월 요금이 붙고, 사용할 때마다 요청 요금이 더해집니다. 열일곱 개면 키 하나일 때보다 열일곱 배의 정책을 유지하고, 열일곱 갈래의 순환과 접근 권한을 추적해야 합니다. "키가 많을수록 무조건 안전하다"는 식으로 단순화할 문제가 아닙니다. 경계를 하나 더 그을 때마다 그 경계를 관리하는 손도 하나 더 늘어납니다.

그럼에도 이 구조가 그 비용을 감수할 만하다고 본 이유는, 나눈 경계가 임의의 개수가 아니라 실제로 접근 주체가 갈리는 자리를 따라 그어졌기 때문입니다. 데이터 저장소, 애플리케이션 S3, 인증, 외부 AI 키, 로그는 서로 다른 서비스가 서로 다른 상황에서 만지는 대상이고, 부트스트랩의 상태·이미지는 환경보다 위에 있는 재료입니다. 경계가 이렇게 의미 있는 자리에 놓이면, 키 하나가 감당하는 폭발 반경이 그 용도 안으로 좁혀지고, 각 키의 정책에 최소 권한을 붙일 여지가 생깁니다. 반대로 경계를 아무 데나 더 잘게 그으면 관리 비용만 늘고 격리의 실익은 크지 않습니다.

이 다이어그램을 처음 봤을 때는 "열쇠가 왜 이렇게 많나" 싶었는데, 하나씩 따라가 보니 개수 자체가 목적은 아니었습니다. 봉투 암호화는 데이터를 감싸는 기술적 토대를 제공할 뿐이고, 실제로 안전을 만드는 것은 "데이터 키를 어느 KMS 키로 감쌀지 나누고, 그 키마다 누가 풀 수 있는지를 좁게 정하는" 설계 판단이었습니다. 그리고 그 판단과는 별개로, 순환은 살아 있는 키의 위생을, 삭제 대기 기간은 키를 잃지 않을 마지막 여유를 각각 맡고 있었습니다. 다이어그램 한 장이 "5 + 2 = 7"이라는 숫자로 짧게 요약해 준 이 구조를, 각 키가 무엇을 감싸고 어떤 스위치가 켜져 있는지까지 따라가 보고 나서야 제대로 이해한 느낌입니다.

## 들어가며 — 점선으로 그려진 리소스 하나

dev·beta·prod 세 환경의 AWS 레퍼런스 아키텍처 다이어그램을 나란히 펼쳐 놓고 Private-data 서브넷 하나만 들여다보면, 아이콘 네 개가 나란히 서 있습니다. Aurora, ElastiCache Valkey, MSK는 실선 테두리의 VPC 안에 온전히 들어가 있는데, 나머지 하나인 MongoDB Atlas만 "external · not managed by Terraform"이라는 설명이 붙은 채 다르게 그려져 있습니다. 세 환경 모두 같은 자리에 같은 방식으로 이 표시가 반복됩니다.

처음 이 다이어그램을 봤을 때는 "인프라 코드가 만들지 않으니 그냥 참고용으로 그려 넣은 것"이라고 넘겼습니다. 그런데 Terraform 코드와 프로젝트의 데이터 흐름 서술을 함께 읽어 보니, 이 점선 하나가 이 시스템의 CQRS 설계 전체를 요약하고 있다는 걸 알게 됐습니다. 쓰기는 Terraform이 직접 만들고 관리하는 Aurora MySQL로 가고, 읽기는 Terraform이 프로비저닝하지 않는 외부 서비스인 MongoDB Atlas로 갑니다. 인프라 코드의 관리 범위 자체가 CQRS의 쓰기·읽기 경계와 정확히 겹치는 셈입니다. 이 글에서는 왜 이 두 모델을 물리적으로 다른 엔진으로 나눴는지, 그리고 Terraform이 만들지 않는 리소스를 인프라 코드에서 어떻게 안전하게 "참조"만 하고 있는지를 코드와 공식 문서를 근거로 짚어 보려 합니다.

## 왜 쓰기와 읽기를 아예 다른 엔진으로 나누는가

CQRS(Command Query Responsibility Segregation)는 데이터를 변경하는 명령(command)과 데이터를 조회하는 질의(query)의 책임을 분리하는 패턴입니다. Microsoft의 Azure Architecture Center는 이 패턴을 두 단계로 구분해서 설명합니다. 하나는 같은 데이터 저장소를 두고 읽기 모델과 쓰기 모델의 로직만 분리하는 방식이고, 다른 하나는 읽기와 쓰기를 아예 서로 다른 데이터 저장소로 나누는 방식입니다. 후자를 택하면 각 모델을 독립적으로 확장할 수 있고, 읽기 쪽에는 문서 데이터베이스를, 쓰기 쪽에는 관계형 데이터베이스를 쓰는 식으로 서로 다른 저장 기술을 자유롭게 고를 수 있다고 설명합니다. 이 프로젝트가 택한 것은 바로 이 두 번째 방식입니다.

프로젝트의 데이터 흐름 서술을 보면 이 구조가 명확하게 드러납니다. 쓰기는 Aurora MySQL이 맡고, 읽기는 MongoDB Atlas가 맡으며, 둘 사이의 동기화는 Kafka(MSK)가 담당하도록 설계돼 있습니다. 왜 하나의 엔진으로 합치지 않았는가를 이해하려면, 쓰기 모델과 읽기 모델이 요구하는 것이 애초에 다르다는 점을 봐야 합니다. 쓰기 쪽은 데이터의 정합성과 트랜잭션 무결성이 우선입니다. 정규화된 스키마로 중복을 줄이고, 관계형 제약 조건으로 잘못된 상태가 만들어지지 않도록 막는 것이 목적입니다. Aurora MySQL이 이 역할을 맡는 것은, MySQL과 호환되는 관계형 엔진으로서 트랜잭션과 외래 키 제약 같은 익숙한 도구를 그대로 쓸 수 있기 때문입니다.

반대로 읽기 쪽은 조회 성능과 화면에 바로 내려줄 수 있는 형태가 우선입니다. Azure Architecture Center의 표현을 빌리면, 읽기 모델은 도메인 로직 없이 표현 계층에 최적화된 데이터 전송 객체(DTO)나 투영(projection)을 만들어 내는 데 집중합니다. 여러 테이블을 조인해서 화면에 필요한 형태로 다시 조립하는 대신, 이미 그 형태로 비정규화돼 있는 문서를 그대로 돌려주는 편이 훨씬 빠릅니다. 이 프로젝트에서 MongoDB Atlas가 맡는 역할이 정확히 이것입니다. RAG 챗봇과 에이전트 서비스가 벡터 검색까지 함께 써야 하는 조회 요구를 감안하면, 관계형 엔진보다 문서 지향 데이터베이스 쪽이 이 요구에 더 맞는 선택입니다.

Azure Architecture Center는 이 분리 방식을 선택할 때 감수해야 할 트레이드오프도 함께 짚습니다. 읽기 저장소와 쓰기 저장소를 나누면 두 저장소 사이의 동기화를 반드시 챙겨야 하고, 메시지 브로커와 데이터베이스를 하나의 분산 트랜잭션으로 묶을 수 없기 때문에 읽기 쪽 데이터가 최신 상태를 즉시 반영하지 못하는 최종적 일관성(eventual consistency) 문제가 생긴다고 설명합니다. 이 프로젝트가 Kafka를 동기화 수단으로 둔 것도 이 문제를 정면으로 인정하고 그에 맞는 도구를 선택한 결과로 볼 수 있습니다. 완벽한 즉시 일관성을 포기하는 대신, 쓰기와 읽기 각각을 그 목적에 맞는 엔진으로 최적화하는 쪽을 택한 것입니다.

## Terraform이 만들지 않는 리소스를 안전하게 참조하는 법

여기서 자연스럽게 드는 의문은, MongoDB Atlas를 Terraform이 만들지 않는다면 인프라 코드는 이 리소스와 어떻게 연결되느냐는 것입니다. 답은 Secrets Manager에 있습니다. 코드를 보면 `{project}/{env}/mongodb-uri`라는 이름의 시크릿이 각 환경마다 하나씩 정의돼 있고, 이 시크릿은 초기값으로 placeholder 문자열만 담은 채 `lifecycle.ignore_changes=[secret_string]` 설정과 함께 선언돼 있습니다. 즉 Terraform은 이 시크릿이 "존재해야 한다"는 사실만 선언할 뿐, 그 안에 실제로 어떤 값이 들어 있는지는 신경 쓰지 않도록 명시적으로 손을 뗀 것입니다.

이 패턴이 왜 안전한지는 AWS Secrets Manager 공식 문서의 설명과 그대로 맞물립니다. 문서는 애플리케이션 소스 코드에 자격 증명을 하드코딩하는 대신, 런타임에 Secrets Manager를 호출해 필요한 순간에 자격 증명을 동적으로 가져오라고 안내합니다. 이렇게 하면 코드나 배포 산출물을 들여다볼 수 있는 사람이 있어도 접속 문자열 자체는 노출되지 않습니다. 그리고 자격 증명이 애플리케이션과 함께 저장되지 않기 때문에, 시크릿을 교체(rotate)할 때 애플리케이션 코드를 고치거나 다시 배포할 필요가 없다는 이점도 함께 설명합니다. MongoDB Atlas의 연결 문자열을 코드 저장소나 환경 변수에 직접 박아 넣는 대신 Secrets Manager 시크릿 하나로 감싸 둔 것은, 바로 이 이점을 그대로 누리기 위한 선택입니다.

`lifecycle.ignore_changes`라는 Terraform 메타 인자의 역할도 이 맥락에서 이해하면 명확해집니다. Terraform 공식 문서는 이 인자를 "리소스가 생성된 후 Terraform 외부의 프로세스에 의해 변경될 수 있는 속성"에 쓰라고 안내합니다. 외부에서 값이 바뀌었는데 Terraform이 다음 `plan`이나 `apply`에서 이 변경을 감지하고 원래 선언된 값으로 되돌리려 하면, 오히려 운영 중인 연결 정보를 덮어써 버리는 사고가 날 수 있습니다. `mongodb-uri` 시크릿에 이 인자를 걸어 둔 것은, 실제 연결 문자열은 운영자가 별도 워크플로(콘솔이나 CLI)로 채워 넣고, 그 값을 Terraform이 건드리지 않겠다는 경계를 코드로 명시해 둔 것입니다.

KMS 키 배정도 눈여겨볼 부분입니다. `mongodb-uri` 시크릿은 Aurora, ElastiCache, MSK가 함께 쓰는 `{env}-data` 키로 암호화됩니다. AWS KMS 공식 문서가 설명하는 키 계층 구조를 보면, KMS 키 자체가 데이터를 직접 암호화하는 것이 아니라, HSM(하드웨어 보안 모듈) 안에서 만들어진 데이터 키가 데이터를 암호화하고, 그 데이터 키는 다시 KMS 키(문서 표현으로는 HSM backing key)로 암호화된 채 저장됩니다. 이렇게 두 겹으로 감싸는 방식 덕분에, 평문 상태의 키 자체가 KMS 바깥으로 나가는 일 없이 암호화된 형태로만 유통됩니다. `{env}-data`라는 이름 하나로 이 네 가지 리소스의 데이터 보호 정책을 통일해 둔 것은, 이 리소스들이 모두 "이 환경의 데이터"라는 같은 성격의 자산이라는 인식을 KMS 키 경계에 그대로 반영한 결과로 읽힙니다.

한 가지 정직하게 짚어야 할 부분이 있습니다. 프로젝트 문서는 Private-data 서브넷을 "MongoDB Atlas Endpoint"용으로 표기해 두었지만, 실제로 이 엔드포인트를 만드는 Terraform 리소스는 코드 어디에도 없습니다. VPC 피어링이나 프라이빗 엔드포인트를 통한 연결은 MongoDB Atlas 공식 문서에서도 지원하는 방식으로 안내하고 있지만, 이 프로젝트에서 그 연결이 실제로 어떤 방식(퍼블릭 IP 액세스 리스트인지, VPC 피어링인지)으로 맺어지는지는 Terraform 코드만으로는 확인할 수 없습니다. 서브넷 이름의 의도와 실제 구현 사이에 아직 채워지지 않은 간극이 있다는 뜻이고, 이 점은 추측 없이 "확인 필요"로 남겨 두는 게 맞다고 생각합니다.

## 읽기 경로 3개 서비스, 쓰기 경로는 그보다 적다 — 경계는 무엇인가

이 프로젝트의 서비스는 여섯 개입니다. 다이어그램은 MongoDB Atlas를 읽는 쪽으로 api-chatbot, api-agent, api-emerging-tech 세 곳을 표시해 둡니다. 다만 Terraform 코드를 열어 보면, `mongodb-uri` 시크릿 읽기 권한이 태스크 역할(Task Role)에 실제로 들어 있는 서비스는 api-chatbot과 api-agent 두 곳뿐입니다. api-emerging-tech의 태스크 역할에는 `openai-api-key` 읽기 권한만 있고 `mongodb-uri` 권한은 없습니다. 다이어그램이 읽기 소비자로 그려 둔 것과 코드에 실제로 새겨진 권한 사이에 이 지점에서도 작은 간극이 있는 셈입니다. 나머지 서비스인 api-auth와 api-bookmark는 Aurora에 대한 `rds-db:connect` 권한을 갖고 있고, api-gateway는 애초에 데이터 저장소 접근 권한 없이 SSM 파라미터만 읽습니다.

이 경계가 어디서 그어지는지를 서비스 성격으로 풀어 보면 답이 나옵니다. api-chatbot과 api-agent는 langchain4j 기반의 RAG·에이전트 서비스로, MongoDB Atlas의 벡터 검색 기능을 실제로 써야 하는 조회 중심 워크로드입니다. api-emerging-tech 역시 AI 관련 업데이트를 모아 보여주는 조회 API입니다. 셋 다 "무언가를 새로 만들거나 바꾸는" 것보다 "이미 있는 데이터를 빠르게 찾아 보여주는" 데 무게가 실려 있습니다. 반면 api-auth는 인증 정보를 다루고 api-bookmark는 사용자의 북마크를 저장하는, 트랜잭션 무결성이 더 중요한 쓰기 중심 서비스입니다.

여기서 흥미로운 점은, CQRS라는 이름이 무색하지 않게 "쓰기 서비스는 오직 Aurora만, 읽기 서비스는 오직 MongoDB Atlas만" 이라는 완전한 대칭으로 나뉘어 있지는 않다는 것입니다. api-chatbot과 api-agent도 대화 세션이나 메시지 같은 데이터는 결국 Aurora 쪽 도메인(`common-conversation` 모듈이 다루는 영역)과 맞물려 있을 가능성이 높습니다. 이 문서의 근거인 Terraform 코드와 아키텍처 사실 정리본에는 각 서비스의 시크릿 접근 권한만 나와 있을 뿐, 서비스 내부 코드가 Aurora와 MongoDB를 정확히 어떻게 나눠 쓰는지까지는 담겨 있지 않습니다. 그래서 이 글에서 확실하게 말할 수 있는 것은 "`mongodb-uri` 시크릿 읽기 권한이 코드로 확인되는 서비스는 api-chatbot과 api-agent 두 곳이고, 다이어그램은 여기에 api-emerging-tech까지 읽기 쪽으로 표기해 둔다"는 인프라 차원의 사실까지이고, 그 서비스들이 애플리케이션 레벨에서 얼마나 순수하게 읽기 전용으로만 동작하는지는 이 인프라 문서의 범위 밖입니다.

그럼에도 이 권한 배정 자체가 실질적인 보안 경계로 작동한다는 점은 분명합니다. Azure Architecture Center가 CQRS의 이점 중 하나로 꼽는 것이 바로 "적절한 도메인 엔티티나 연산에만 쓰기 권한을 부여할 수 있다"는 보안 측면인데, 이 프로젝트에서는 그 원칙이 IAM 태스크 역할 단위로 코드에 그대로 새겨져 있습니다. api-bookmark가 실수로 MongoDB Atlas 시크릿을 읽으려 해도, 애초에 그 권한 자체가 태스크 역할에 없기 때문에 시도 자체가 거부됩니다. 애플리케이션 코드가 실수하지 않기를 바라는 대신, 인프라 계층에서 접근 가능한 리소스의 목록 자체를 서비스별로 좁혀 둔 것입니다.

## 동기화는 코드 범위 밖이라는 정직한 경계선

CQRS를 쓰기·읽기 두 저장소로 나누는 순간 반드시 따라오는 질문이 있습니다. 두 저장소를 누가, 어떻게 맞춰 주느냐는 것입니다. 이 프로젝트의 답은 Kafka(MSK)입니다. Aurora에 쓰기가 일어나면 이벤트가 발행되고, 그 이벤트를 소비해서 MongoDB Atlas 쪽 읽기 모델을 갱신하는 방식으로 설계돼 있습니다. Azure Architecture Center도 이 방식을 표준적인 패턴으로 소개합니다. 쓰기 모델이 데이터베이스를 갱신할 때 이벤트를 발행하고, 읽기 모델이 그 이벤트를 받아 자신의 데이터를 새로 고치는 구조입니다.

다만 Terraform 코드가 실제로 보장하는 것은 이 지점에서 멈춥니다. 인프라 코드는 MSK 클러스터가 존재하고, api-agent 서비스가 `kafka-cluster:*` 권한으로 이 클러스터에 접근할 수 있다는 것까지만 만듭니다. Aurora의 변경 사항이 실제로 이벤트로 발행되는 로직, 그 이벤트가 정확히 어떤 스키마를 쓰는지, MongoDB Atlas 쪽에서 이 이벤트를 소비해 문서를 갱신하는 컨슈머 로직이 얼마나 탄탄한지는 전부 애플리케이션 코드의 영역이고 Terraform 코드에는 등장하지 않습니다. 프로젝트의 아키텍처 사실 정리 문서도 이 지점을 "Terraform은 인프라만 제공하고 애플리케이션 동기화 로직은 코드 범위 밖"이라고 분명히 선을 긋고 있습니다.

이 경계선이 다소 허전하게 느껴질 수도 있습니다. 하지만 인프라 코드가 담당할 수 있는 것과 없는 것을 뒤섞지 않고 정직하게 나눠 둔 것이라고 보는 편이 더 정확합니다. Terraform이 보장하는 것은 "이벤트를 주고받을 수 있는 통로가 존재하고, 정해진 서비스만 그 통로에 접근할 수 있다"는 것까지입니다. 그 통로 위로 오가는 메시지가 정확한지, 소비자가 멱등성을 지키며 중복 이벤트를 걸러내는지는 인프라 문서가 답할 수 있는 질문이 아닙니다. 프로젝트의 다른 문서에서 Redis 기반 멱등성 처리를 별도로 두고 있다는 사실도, 이 동기화 신뢰성을 Kafka와 인프라만으로 해결하지 않고 애플리케이션 계층에서 한 겹 더 보강하고 있다는 정황으로 볼 수 있습니다. 다만 이 부분의 상세 구현은 이 인프라 문서의 근거 범위 밖이라 여기서 더 단정하지는 않겠습니다.

## 결론 — 인프라 다이어그램에 "안 만든 것"을 그려 넣는 실용적 이유

이 글을 쓰면서 처음 품었던 질문으로 돌아가 보면, 답은 생각보다 단순했습니다. MongoDB Atlas를 다이어그램에 그려 넣은 이유는 이 시스템의 완전한 그림을 그리기 위해서입니다. Terraform이 만든 것만 그리면, 이 시스템이 실제로 어디서 데이터를 읽어 오는지에 대한 그림 하나가 통째로 비어 버립니다. "관리하지 않는다"는 사실과 "존재하지 않는다"는 사실은 다릅니다. 점선 하나로 이 차이를 남겨 둔 것은, 온콜 엔지니어나 이 프로젝트에 새로 합류하는 사람이 다이어그램만 보고도 "이 리소스는 우리 Terraform state에는 없지만 이 시스템의 데이터 흐름에는 분명히 관여한다"는 사실을 곧바로 알아차릴 수 있게 해 줍니다.

이번 조사를 하면서 개인적으로 얻은 인사이트는, CQRS에서 "쓰기와 읽기를 다른 저장소로 나눈다"는 설계 결정이 애플리케이션 코드의 문제만은 아니라는 점이었습니다. 이 프로젝트에서는 그 결정이 IAM 태스크 역할의 경계, KMS 키의 배정, Secrets Manager 시크릿의 소유권, 그리고 Terraform state의 관리 범위까지 인프라 코드 전반에 걸쳐 일관되게 반영돼 있었습니다. CQRS를 설계 문서에만 적어 두고 끝내는 것과, 그 경계를 인프라 코드 구조 자체로 강제하는 것 사이에는 꽤 큰 차이가 있다는 것을 이번에 다시 확인한 셈입니다. 그리고 그 경계를 지키는 일이 때로는 "무언가를 새로 만드는 것"이 아니라 "무언가를 만들지 않기로 하고, 그 사실을 정확하게 기록해 두는 것"으로 나타난다는 점도 함께 남겨 둡니다.

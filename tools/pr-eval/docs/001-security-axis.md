# 001. 보안 축(`R-I`) 추가 설계

**상태**: **반영됨** — §8 을 통과해 §7 의 파일 여섯을 고쳤다. 검증 기록은 `runs/tech-n-ai-backend-pr33/verify-001/`(추적되지 않는다).
**적은 날**: 2026-09-01 · **고친 날**: 2026-09-01 (적대적 검토 반영은 §10, 검증 결과 반영은 §8-2)

---

## 0. 무엇을 정하는 문서인가

eval-bot 을 보강하려고 ISO/IEC 25010(품질)·OWASP ASVS·ISMS-P(보안) 검사를 프로세스로 추가하는 안을 검토했다.
검토 결과 **표준 셋을 검사 절차로 얹지 않고, 실제로 비어 있는 보안 축 하나만 채운다.**
이 문서는 그 결정과 근거, 바꿀 파일, 그리고 도입 전에 통과해야 할 검증을 적는다.

배경은 하나다. 현재 8축에 **보안 축이 없다.** 보안에 닿는 항목은 두 곳에 흩어져 있다 —
`R-H` 의 "하드코딩 자격증명"(`profiles/backend.md:215`)과 `R-D` 의 `X-Internal-Api-Key` 검증
(같은 파일 §4). 축이 없으니 위원 프롬프트에 "무엇을 볼 것인가" 가 없고, S1 커버리지 판정에도 안 잡힌다.

---

## 1. 결정 요약

| 표준 | 채택 형태 | 왜 |
|---|---|---|
| **OWASP ASVS 5.0.0** | 검사 절차가 아니라 **새 축 `R-I` 의 근거 문헌**(출처 등급 B) | 축자 인용이 가능하고 공개돼 있다. 절차로 돌리면 앵커가 안 붙는 지적이 대량으로 나온다 |
| **ISO/IEC 25010** | 절차 추가 없음. **축 정의표 각주로 대응만 표기** | 8축이 이미 특성 대부분을 덮는다. 빈 곳은 보안 하나뿐이다 |
| **ISMS-P 인증기준** | **넣지 않는다** | 조직에 대한 인증이라 심사 증거가 PR diff 에 없다 |

## 2. 왜 표준을 검사 절차로 얹지 않는가

근거 셋이다. 셋 다 하니스가 이미 문서에 적어 둔 규칙에서 나온다.

**앵커가 안 붙는다.** 표준 요구사항 상당수는 설정·아키텍처·런타임 증거를 봐야 판정된다.
봇이 보는 것은 `eval_sha` 의 diff 다. 앵커 없는 지적은 `00-criteria.md` §1 의 I-1 에 걸리고,
성립해도 요약 본문으로 밀려 무게를 잃는다.

**인용이 결론까지 안 간다.** *"표준이 X 를 요구한다"* 와 *"이 줄이 X 를 위반한다"* 는 다른 명제다.
이건 V2(인용 검증자)가 잡도록 설계된 바로 그 유형이고(`_memory/learnings.md` L0-12),
라운드 비용만 쓰고 삭제될 코멘트를 양산한다.

**시간이 없다.** Stage 1 라운드 1 만 약 50분이고 락 TTL 은 3시간이다(`CLAUDE.md` §6-1, 줄이지 말라고 명시).
위원을 늘리면 벽시계가 TTL 벽으로 간다. 위원당 축을 늘리면 8축을 4명에 나눈 이유
— *"한 세션이 여덟 축을 한꺼번에 보면 눈에 먼저 띄는 몇 개에서 멈춘다"*(`README.md`) — 를 스스로 깬다.
그래서 **위원은 4명 그대로 두고, 새 축은 조건부로 발동시킨다.**

## 3. `R-I` 축 정의

### 3-1. 이름과 뜻

| 축 | 이름 | 이 프로파일에서의 뜻 |
|---|---|---|
| **R-I** | 보안 | 권한 없는 주체가 통과하는가. 나가면 안 될 값이 나가는가. 믿으면 안 될 입력을 믿는가 |

`R-D` 와의 경계는 이렇게 긋는다 — **`R-D` 는 "계약대로 동작하는가", `R-I` 는 "권한 없는 주체가 통과하는가".**

### 3-2. 조건부 축 — 발동 조건

프런트 프로파일의 `R-G` 가 이미 조건부 축이다(`profiles/frontend.md:37`). 같은 방식을 쓴다.

Phase 0 에서 오케스트레이터가 판정한다. 변경 파일 목록과 diff 추가 줄에 아래 중 **하나라도** 걸리면 해당,
하나도 없으면 비해당이다. **아래 명령을 그대로 돌리고 매치 수를 `rounds/round-NN.md` 에 적는다.**
명령을 정해 두지 않으면 "비해당" 이라는 부정 명제가 라운드마다 다른 패턴으로 판정된다
(`00-criteria.md` §2 계수 규칙 · L0-19).

| 신호 | 어떻게 본다 |
|---|---|
| **1** 인증·인가 코드 | 변경 파일이 `common/security/` · `api/auth/` · `api/gateway/` 아래 |
| **2** 새 HTTP 엔드포인트 | diff 추가 줄에 `@GetMapping` · `@PostMapping` · `@PutMapping` · `@DeleteMapping` · `@RequestMapping` |
| **3** 사용자별 데이터 경로 | 변경 파일이 `api/bookmark/` · `common/conversation/` 아래 |
| **4** 자격증명·시크릿 | **소스·설정 파일의** diff 추가 줄에 `password` · `secret` · `credential` · `apiKey` · `accessToken` · `refreshToken` · `authorization` (대소문자 무시) |
| **5** 외부 텍스트를 믿는 경로 | 변경 파일이 `api/agent/` · `api/chatbot/` · `client/scraper/` · `client/rss/` · `batch/source/` 아래 |

```bash
# 두 SHA 는 `pr-eval.sh meta <저장소> <PR번호>` 로 읽는다(봇 토큰 불필요).
# Stage 1 의 구간은 base_sha…eval_sha 다. 아래 git 명령은 평가 대상 저장소 워크트리에서 돈다.
B=<meta.base_sha>; S=<meta.eval_sha>
git diff --name-only $B...$S | grep -cE '^(common/security|api/auth|api/gateway)/'          # 신호1
git diff -U0 $B...$S | grep '^+' | grep -cE '@(Get|Post|Put|Delete|Request)Mapping'         # 신호2
git diff --name-only $B...$S | grep -cE '^(api/bookmark|common/conversation)/'              # 신호3
git diff -U0 $B...$S -- '*.java' '*.kt' '*.yml' '*.yaml' '*.properties' '*.gradle' '*.tf' '*.sh' 'Dockerfile*' \
  | grep '^+' | grep -icE 'password|secret|credential|api[-_]?key|access[-_]?token|refresh[-_]?token|authorization'   # 신호4
git diff --name-only $B...$S | grep -cE '^(api/agent|api/chatbot|client/(scraper|rss)|batch/source)/'   # 신호5
```

> **신호4 에서 `token` · `email` 단독 매치를 뺀 이유 — 실측이다** (2026-09-01, `git log -60` 범위).
> 원안(`token|password|secret|apiKey|email`)을 최근 main 커밋에 돌렸더니 `436868a`(챗봇 LLM 토큰 사용량 계측)가
> **48건**을 냈는데 전부 `TokenUsage`·`maxTokens`·`inputTokens` 같은 **모델 토큰 계량**이었고,
> 문서만 고친 `346515c`(ERD·아키텍처 다이어그램)도 **6건**을 냈는데 전부 mermaid 노드 이름 `TokenService` 였다.
> 이 저장소에서 `token` 은 인증 토큰보다 LLM 토큰이 훨씬 흔하다.
> 좁힌 안은 그 커밋들에서 전부 **0**을 냈고, 실제 자격증명을 다룬 `c784870`
> (`langchain4j.open-ai.chat-model.api-key`) **18건** · `26957b5`(terraform IAM·시크릿) **3건**은 그대로 잡았다.
> 확장자를 목록으로 한정한 것도 같은 실측에서 왔다 — 거짓 매치는 전부 `.md`·`.mmd`·`.drawio` 였다.
> 좁힌 신호4 는 최근 60커밋 중 **9건**에서 발동했고 그 전부가 신호1 매치 0 이었다. 다른 신호가 못 잡는 자리를 잡는다.

> **`batch/source/` 를 신호5 에 넣은 이유** — §3-5 의 볼 것이 *"`batch-source` 가 스크래핑한 텍스트를 그대로 저장하는가"*
> 를 이미 담고 있는데 발동 조건에는 그 경로가 없었다. 볼 것과 발동 조건이 어긋나면 축이 켜지지 않은 채 지시만 남는다.

비해당이면 S1 커버리지 판정에 *"`R-I`: 비해당 — 위 다섯 신호 매치 0"* 로 적는다.
`00-criteria.md` §5 유형별 조정표가 다른 축에 하는 일과 같다.

### 3-3. 위원 배정

**J3(인터페이스 계약·부하 적합성)에 붙인다.** 인가 누락은 `R-D` 와 같은 자리 — 컨트롤러와 엔드포인트 —
에서 보이므로 중복 제거가 자연스럽다. 위원을 5명으로 늘리지 않는다(§2 시간 근거).

중복 제거 우선순위는 그대로 `J1 > J2 > J3 > J4` 다. `R-I` 를 앞으로 당기지 않는다 —
설계·데이터가 틀렸다는 판단이 나머지의 전제라는 이유(`README.md`)는 보안 축이 생겨도 그대로다.

**받아들이는 비용 — `R-I` 가 발동하면 J3 만 축을 셋 본다.** 위원을 안 늘리기로 한 대가다(§2).
그런데 `R-I` 가 발동하는 PR 은 대개 컨트롤러와 엔드포인트가 늘어난 PR 이라 `R-D`·`R-E` 도 같이 무거워진다 —
**부담이 가장 큰 판에서 축이 하나 더 붙는다.** *"한 세션이 여러 축을 한꺼번에 보면 눈에 먼저 띄는 몇 개에서 멈춘다"* 는
§2 의 근거가 J3 안에서 작게 재현될 수 있다. 그래서 둘을 건다.

- 발동한 라운드에서는 **J3 프롬프트에 `R-I` 절을 `R-E` 앞에 놓는다.** 신호표가 동결 목록과 I-8 에 쓰는 것과 같은 방식이다
  (`01-stages.md` §10).
- **§8 검증에서 J3 를 3축으로 한 번 돌려** `R-D`·`R-E` 판정이 기존 판보다 얇아지지 않는지 본다(§8-2).

`02-judges.md` §2 의 위원 헤더 형식이 `(리뷰 축 R-x · R-y)` 로 축 둘을 전제하므로 셋을 받을 수 있게 고쳐야 한다(§7).

### 3-4. 두 항목을 이 축으로 옮긴다

**옮기지 않고 새로 쓰면 같은 결함을 두 축이 잡는다.** L0-18 이 배운 "축이 코멘트 사이를 옮겨 다니는" 문제가
설계 시점에 생긴다.

| 항목 | 지금 | 옮긴 뒤 |
|---|---|---|
| `X-Internal-Api-Key` 검증 누락 | `R-D` 볼 것 (`profiles/backend.md:166`) | `R-I` |
| *"새 내부 엔드포인트에 `X-Internal-Api-Key` 검증이 없어…"* 치명 예시 | `R-D` 등급 예시 (`:185`) | `R-I` (§3-7 첫 줄과 같은 문장이다) |
| 하드코딩된 자격증명·API 키 | `R-H` 볼 것 (`:215`) | `R-I` |
| *"민감 정보를 로그에 찍는가"* | `R-H` 볼 것 (`:216`) | `R-I` |
| *"중대: API 키가 소스에 하드코딩됐다"* | `R-H` 등급 예시 (`:229`) | `R-I` |

`R-H` 의 "하드코딩된 URL" 은 보안이 아니므로 `R-H` 에 남긴다.
`R-H:216` 의 *"예외를 삼키고 아무것도 안 남기는가"* 도 `R-H` 에 남는다 — §3-6 이 그은 대로
**`R-H` 는 남아야 할 것이 안 남는 쪽, `R-I` 는 남으면 안 될 것이 남는 쪽**이다. 한 줄에 붙어 있으니 쪼개야 한다.

**`R-D:167` 의 *"gateway 가 붙이는 헤더를 서비스가 신뢰하는가"* 는 경계에 걸친다.** `R-D` 에 남기되
*"그 헤더가 없거나 위조됐을 때 인증 주체가 뒤바뀌는가"* 는 `R-I` 다. `R-D` 는 헤더 계약의 유무,
`R-I` 는 그 헤더를 믿어도 되는가를 본다.

### 3-5. 볼 것

- **인가 누락** — 요청자가 그 리소스의 주인인지 확인하지 않고 id 로 조회·수정·삭제하는가.
  사용자별 데이터를 다루는 경로에 새 엔드포인트가 생겼는데 소유자 검사가 없는 자리. (ASVS 8.2.2)
- **인증 주체를 클라이언트가 준 값에서 읽는가** — 요청 파라미터·바디의 `userId` 를 그대로 쓰는가,
  검증된 토큰에서 꺼내는가.
- **내부 전용 경로가 열렸는가** — 새 내부 엔드포인트에 `X-Internal-Api-Key` 검증이 있는가.
  gateway 를 우회해 직접 부를 수 있는가.
- **토큰·자격증명·개인정보가 로그에 남는가** — `log.` 인자에 access token, refresh token,
  OAuth 인가 코드, 비밀번호, 이메일이 **해시나 마스킹 없이** 그대로 들어가는가. (ASVS 16.2.5)
- **같은 값이 응답에 실리는가** — 응답 DTO 가 그대로 내보내는가. **근거는 코드 사실(C)로 댄다.**
  ASVS 16.2.5 는 로깅만 말한다 — 응답까지 그 인용으로 덮으면 I-3(출처 등급 초과)이다.
- **시크릿 하드코딩** — API 키·비밀번호·서명 키가 소스나 설정 파일에 값으로 들어갔는가.
- **외부 입력이 질의에 그대로 들어가는가** — 문자열로 조립한 JPQL·네이티브 쿼리·MongoDB 질의.
  파라미터 바인딩이나 QueryDSL 을 우회한 자리.
- **LLM 응답이나 수집한 외부 텍스트를 검증 없이 믿는가** — `api-agent`·`api-chatbot` 이 모델이 낸 값을
  그대로 질의나 도구 호출 인자로 넘기는가. `batch-source` 가 스크래핑한 텍스트를 그대로 저장하는가.

### 3-6. 보지 않을 것

- 의존성 라이브러리의 알려진 취약점·버전 → **diff 로 판정할 수 없다.** 의존성 스캐너의 일이다.
- TLS 종단·보안그룹·WAF 같은 인프라 설정 → `devops/terraform/` 이 바뀐 PR 에서 **코드 사실로 확인되는 것만.**
  운영 콘솔의 실제 상태는 안 본다.
- 정책 문서·권한 검토 기록의 유무 → 조직 심사 항목이다. 안 본다(§6).
- 상태 코드·응답 **형태**·직렬화 → `R-D`. 형태가 아니라 **나가면 안 될 값이 그 형태에 담기는** 것만 이 축이다
- 예외를 삼켜 로그가 **안** 남는 것 → `R-H`(관측 가능성). 이 축은 *남으면 안 될 것이 남는* 쪽을 본다.
- 외부 의존이 죽었을 때 같이 죽는가 → `R-F`

### 3-7. 등급 예시

- **치명**: 새 조회 엔드포인트가 경로의 id 로 바로 조회해, 다른 사용자의 데이터가 그대로 나간다.
- **치명**: 새 내부 엔드포인트에 `X-Internal-Api-Key` 검증이 없어 gateway 를 우회해 직접 호출된다.
- **중대**: 요청 바디의 `userId` 를 그대로 써서, 값을 바꾸면 남의 데이터에 쓴다.
- **중대**: 로그인 응답을 통째로 로그에 남겨 refresh token 이 평문으로 찍힌다.
- **경미**: 예외 메시지에 내부 쿼리나 스택트레이스를 담아 응답한다.

### 3-8. 무효 조건은 추가하지 않는다

`00-criteria.md` §1 의 I-1 ~ I-8 로 충분하다. 특히 I-1(앵커)과 I-3(출처 등급 초과)이
표준 인용을 남용하는 지적을 이미 막는다. **조건을 늘리면 위원 프롬프트만 길어지고 판정은 안 달라진다.**

## 4. ASVS 를 근거로 쓰는 방법

`README.md` "기준의 출처" 표에 행을 더한다. Google eng-practices 를 쓴 방식과 같다 —
**인용문을 축자로 적고, 그 인용문이 결론까지 말하는 범위 안에서만 쓴다**(I-3).

버전을 고정한다: **OWASP ASVS 5.0.0**. 공식 원문 `5.0/en/0x01-Frontispiece.md` 에 *"Version 5.0.0, May 2025"* 라고 적혀 있다.
**일자와 발표 행사는 그 원문에서 확인되지 않으므로 적지 않는다**(`미검증` 을 남길 바에 안 쓴다).
5.0 은 4.x 와 장 번호가 다르므로 인용할 때 버전을 반드시 함께 적는다.

| 하니스의 규칙 | 출처 | 근거가 된 문장 |
|---|---|---|
| `R-I` 의 첫 항목이 인가 누락인 이유 | OWASP ASVS 5.0.0, V8 Authorization, 8.2.2 (Level 1) | "Verify that the application ensures that data-specific access is restricted to consumers with explicit permissions to specific data items to mitigate insecure direct object reference (IDOR) and broken object level authorization (BOLA)." |
| 토큰·자격증명이 로그에 남는 것을 결함으로 보는 근거 | 같은 문서, V16 Security Logging and Error Handling, 16.2.5 (Level 2) | "Verify that when logging sensitive data, the application enforces logging based on the data's protection level. For example, it may not be allowed to log certain data, such as credentials or payment details. Other data, such as session tokens, may only be logged by being hashed or masked, either in full or partially." |

**두 인용은 2026-09-01 에 공식 저장소 `OWASP/ASVS` 태그 `v5.0.0` 의
`5.0/en/0x17-V8-Authorization.md` · `0x25-V16-Security-Logging-and-Error-Handling.md` 와 축자 대조했다.**
Level 표기(8.2.2 = 1, 16.2.5 = 2)도 원문 표의 마지막 칸과 맞다.

> **16.2.5 는 마지막 문장까지 실어야 한다.** 초안은 *"…credentials or payment details."* 에서 잘랐는데,
> 잘린 문장이 바로 **세션 토큰**을 다룬다 — *"Other data, such as session tokens, may only be logged by being
> hashed or masked, either in full or partially."* 잘린 인용으로는 "refresh token 이 평문으로 찍힌다" 가
> 왜 결함인지가 인용 밖 주장이 되고, 그대로 두면 I-3 다. 전문을 실으면 인용이 결론까지 말한다.
> **인용을 줄여 붙일 때 잘려 나간 절이 결론을 약하게 하는지부터 본다** — L0-12 가 기록한 바로 그 유형이다.

**ASVS 를 전건 점검표로 돌리지 않는다.** 축 정의문의 근거로만 쓴다.
위원 프롬프트에는 위 두 인용만 싣고, 다른 요구사항을 쓰려면 그때 원문을 다시 열어 축자로 옮긴다.

## 5. ISO/IEC 25010 — 각주로만 둔다

`profiles/backend.md` §1 축 정의표 아래에 대응표를 각주로 한 번 둔다. 검사 절차는 만들지 않는다.

| 25010 특성 | 대응 축 |
|---|---|
| 기능 적합성 | `R-A` · `R-B` |
| 성능 효율성 | `R-E` |
| 호환성 | `R-D` |
| 신뢰성 | `R-C` · `R-F` |
| 보안 | **`R-I`** ← 이 문서가 채우는 자리 |
| 유지보수성 | `R-G` · `R-H` |
| 상호작용 능력 | frontend `R-H`(접근성) |
| 유연성 · 안전성 | 이 저장소의 PR 에서는 거의 발동하지 않는다 |

**이 표를 게시되는 리뷰에 인용하지 않는다.** 두 가지 이유다.

첫째, ISO/IEC 25010 은 유료 표준이라 원문을 열 수 없었다(`iso.org` 가 403 을 준다).
축자 인용과 URL 을 댈 수 없으므로 **출처 등급 B 의 조건을 못 맞춘다.** 위 특성 이름은 `미검증`이다 —
채택하는 사람이 구매본과 대조해야 한다.

둘째, 대응표는 *"우리 축이 무엇을 덮고 무엇이 비었나"* 를 보려고 만든 것이다.
그 목적은 이 문서 안에서 끝났다 — 빈 곳이 보안 하나라는 것을 확인했고, §3 이 그것을 채운다.
25010 을 절차로 돌리면 유연성·안전성처럼 **매번 "비해당" 만 찍히는 칸**이 생기는데,
`01-stages.md` §10 이 새 검사를 넣기 전에 묻게 한 질문 — *"이 조건이 거짓이 되는 라운드가 실제로 있는가"* —
에 그 칸들은 "없다" 로 답한다.

## 6. ISMS-P 는 넣지 않는다

ISMS-P 는 **조직에 대한 인증**이다. 심사 증거가 정책 문서·권한 검토 대장·위탁 계약서·조직도인데
PR diff 에는 그런 것이 없다. 코드에 닿는 것은 개발보안·접근통제·암호화·개인정보 처리 쪽 일부 항목이고,
그마저도 §3-5 의 볼 것 두 줄(개인정보가 로그·응답에 실리는가, 시크릿 하드코딩)로 흡수된다.

인증기준을 인용해 "위반" 이라고 쓰기 시작하면 I-3 위반이 대량으로 난다.
그리고 **저자가 코드로 반박할 수단이 없는 지적**이라 V3(저자 반박자)가 전부 걷어낸다.

> 이 절은 ISMS-P 인증기준의 항목 수를 인용하지 않았다. 원문을 확인하지 않았기 때문이다
> (`00-criteria.md` §2 계수 규칙 · L0-19).

## 8. 도입 전 검증 — 이걸 통과해야 반영한다

**축을 늘리기 전에 실측한다.** 안 하면 하니스가 스스로 금지한 "항상 참이거나 항상 거짓인 상수 검사" 를
하나 더 만드는 것이 된다(`01-stages.md` §10).

검증은 둘로 나뉜다. **8-1 은 위원 없이 명령만으로 되고 이미 끝냈다. 8-2 는 세션을 띄워야 한다.**

### 8-1. 발동 판정이 양쪽으로 갈리는가 — **끝났다 (2026-09-01, D등급)**

§3-2 의 명령을 각 PR 의 **게시 기준 SHA**(`base_sha…eval_sha`)로 그대로 돌린 결과다.

| 대상 | 신호1 | 신호2 | 신호3 | 신호4 | 신호5 | 판정 | 기대 |
|---|---|---|---|---|---|---|---|
| **PR #33** 북마크 조회 이벤트 수집 · 일별 리포트 API (게시 기준 SHA 에서 21파일) | 0 | **3** | **14** | 0 | 0 | **해당** | 해당 ✔ |
| **PR #34** 신기술 다건 저장 리팩토링 (게시 기준 SHA 에서 5파일) | 0 | 0 | 0 | 0 | 0 | **비해당** | 비해당 ✔ |

현재 head(각각 23·9파일)로 돌려도 결론은 같다 — #33 은 신호2 =3 · 신호3 =16, #34 는 전부 0 이다.

> **초안이 틀렸던 두 가지를 여기서 고쳤다.** 하나, 초안은 *"PR #33 이 §3-2 신호 중 셋에 걸린다"* 고 썼는데
> 실제로는 **둘**(신호2 · 신호3)이다. 둘, 초안의 파일 수 23·9 는 **현재 head 기준**인데 절차는 게시 기준 SHA 를
> 쓰라고 한다. 그 SHA 에서는 21·5 다. 세는 기준을 안 적으면 수치가 재현되지 않는다(`00-criteria.md` §2 · L0-13).

> **이 시험만으로는 신호4 를 검증할 수 없다.** 두 PR 모두 신호4 매치가 0 이라,
> 초안이 스스로 지목한 위험(*"`email`·`token` 문자열 매치가 넓다"*)이 이 시험에서는 **거짓이 될 수 없었다** —
> `01-stages.md` §10 이 금지한 상수 검사다. 그래서 신호4 는 두 PR 이 아니라 **최근 main 커밋 60건**에 돌려 따로 쟀고,
> 그 결과로 §3-2 를 고쳤다(근거는 §3-2 각주).

### 8-2. 축이 실제로 무언가를 잡는가 — **끝났다. 통과 (2026-09-01)**

PR #33 의 게시 기준 SHA 에서 두 번 돌렸다.

1. **`R-I` 축 하나만 든 위원 1인.** 나온 지적을 반박자에 한 번 통과시킨다.
2. **J3 를 3축(`R-D`·`R-E`·`R-I`)으로 한 번.** `R-D`·`R-E` 판정을 PR #33 의 게시된 판
   (`R-D` 5건 — C-01·C-05·C-07·C-08·C-16 · `R-E` 1건 — C-06, `runs/tech-n-ai-backend-pr33/`)과 나란히 놓고 읽는다.

판정은 이렇게 가른다.

- **1 에서 반박을 통과한 지적이 나오고, 2 에서 `R-D`·`R-E` 가 기존 판보다 얇아지지 않으면** §7 을 반영한다.
- **2 에서 `R-D`·`R-E` 가 눈에 띄게 얇아지면** §3-3 의 배치(`R-I` 절을 `R-E` 앞)로 다시 돌리고,
  그래도 얇아지면 J3 3축을 포기하고 위원 배정을 다시 정한다.

#### 결과

**둘 다 통과했다. §7 을 반영했다.**

**시험 1** — `R-I` 단독 위원이 확정 결함 1건(치명 · IDOR)을 냈고 **반박자가 확정에서 빼지 못했다**
(판정 `근거 축소`, 등급 치명 유지). 반박자는 여섯 경로를 전수로 훑어 소유자 검사 부재를 재현했고
ASVS 8.2.2 인용을 공식 저장소 원문과 축자 대조했다. 축소를 지시한 둘 중 하나는 `grep` 계수 오류(4 → 5),
다른 하나는 처방의 단정 — 처방이 지목한 `findBookmarkById` 가 던지는 `UnauthorizedException` 은
`AUTH_FAILED("4001")` → **401** 이라 설계서가 요구한 403 이 아니다.
**이 두 번째 축소가 게시된 C-01 의 방향 칸과 독립으로 일치했다** — 반박자 질문 ⑥ 이 설계대로 작동한 자리다.

**시험 2** — J3 3축 판이 기존 판의 `R-D`·`R-E` **6건을 전건 재현**했고(누락 0),
`R-D` 확정 결함이 5 → 6 으로 늘었다. 기존 판이 한 코멘트에 묶어 둔 것(C-01·C-05·C-08)을
저자가 따로 고칠 수 있는 단위로 쪼갠 결과다. `R-E` 에서는 기존 판에 없던 왕복 횟수 지적이 하나 나왔고,
원자성 갈래는 위원이 스스로 *"J2 의 `R-C` 영역"* 이라고 잘라 냈다. **얇아지지 않았다.**

**함께 관측된 것 — 등급이 축 배정에 따라 흔들린다.** 소유자 검사 누락에 `R-I` 단독 위원은 `치명`,
J3 3축 위원은 `중대` 를 매겼다(기존 판 C-01 은 `치명`). 축을 하나만 든 위원은 자기 축을 무겁게 본다.
새 장치는 만들지 않는다 — 반박자와 `00-criteria.md` §7 판 전체 대조가 이 자리를 본다.
`_memory/learnings.md` 에 L0-29 로 남겼다.

**검증 설계에서 문서와 다르게 한 것** — `frozen.md` 를 위원 프롬프트에 싣지 않았다.
`01-stages.md` §3-1 은 싣게 하지만, PR #33 의 `frozen.md` 는 이미 끝난 판의 결론이고
그 F-01 이 곧 *"소유자 검증도 `isDeleted` 검사도 없다"* 다 — `R-I` 가 잡아야 할 답 그 자체다.
그걸 주고 *"축이 무언가를 잡는가"* 를 물으면 자기참조가 된다. 재현해야 할 조건은 `frozen.md` 가 비어 있던 라운드 1 이다.
- **1 에서 0건이 나오면 그 자체로는 축을 버릴 근거가 아니다.** 위원이 사유를 코드 사실로 적었는지 본다 —
  적었으면 그건 `R-I` 가 "결함 없음" 을 근거와 함께 판정한 것이고, S1 커버리지가 요구하는 형태 그대로다.
  **PR 한 건의 0건으로 축을 폐기하지 않는다.** `01-stages.md` §4 가 S1 을 *"8축 각각 코멘트 ≥1건"* 으로
  걸지 않은 이유가 그대로 여기 적용된다 — **"≥1건이어야 채택" 은 위원에게 없는 결함을 만들라는 압력이다.**
  대신 §3-2 의 신호가 지난 60커밋에서 몇 번 발동했는지를 함께 보고 판단한다.

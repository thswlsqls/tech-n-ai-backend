# 블로그 시리즈 주제 설계도 세트 작성

지시자가 준 상세 요구사항을 여러 단편으로 쪼개, 기술 블로그 **시리즈**의 주제 설계도 세트를 만든다.
세트는 **단편 설계도 여러 개 + 인덱스(README) md 파일 하나**다.

이 스킬은 형제 스킬 `plan-blog-topic`(단편 하나)을 **시리즈로 확장한 것**이다.
단편 한 편의 설계도 형식·작성 규칙·검증은 `plan-blog-topic`을 그대로 따른다. 여기서 다시 적지 않는다.
이 스킬이 더하는 것은 셋뿐이다: **(1) 적정 편수 결정 (2) 인덱스 작성 (3) 단편 사이 인용 관계.**

본보기는 `docs/reference/writings/devops/topics/` 폴더 전체다 — 단편 파일들 + `README.md` 인덱스 + `series-*.md`.
"상세 요구사항 → 시리즈 기획"의 방식은 `docs/reference/writings/prompts/`의 추출 프롬프트들이 보여준다.

이 스킬도 글을 쓰지 않는다. 기획 문서 세트까지만 만든다. 완성 글은 각 단편 설계도를 `write-tech-blog`에 넘겨 쓴다.

CLAUDE.md 두 원칙(외부 자료 참조 원칙, 사람이 검증하는 텍스트 작성 규칙)은 `plan-blog-topic`과 동일하게 지킨다.

## 산출물의 정의

한 디렉터리에 들어가는 설계도 세트다.

- **단편 설계도 N개** — 각 파일은 `plan-blog-topic`의 "산출물의 정의" 형식을 그대로 따른다. 번호 접두사(`01-`, `02-` …)를 붙인다.
  - 각 단편 끝에 **시리즈 인용 관계** 절을 둔다: 이 단편이 시리즈 어느 편에 인용·확장되는지, 또는 "시리즈 외 독립 자산"인지 표시한다(`devops/topics/`의 단편들이 이 신호를 남긴다).
- **인덱스(`README.md`)** — `devops/topics/README.md`를 본보기로 다음을 담는다.
  - 시리즈의 한 줄 정의와 1차 소스
  - **단편 목록 표** — 번호·제목·다루는 관점·근거·분량
  - (요구사항이 메타 글을 요청하면) **시리즈/메타 글 표** — 단편들을 하나의 서사로 묶는 편들
  - **폐기·병합 로그** — 후보였다가 뺀 주제와 그 이유(투명성)
  - **작성 가이드** — 인용 정책, 본문 언어, 수치 표기, 다이어그램 등 공통 규칙
- **시리즈 메타 파일**(선택, `series-*.md`) — 단편을 하나의 서사로 묶는 메타 글이 필요할 때만. 단편이 이미 답한 "왜"를 반복하지 않고 인과 사슬·누적 효과만 더한다(`devops/topics/series-02-...`가 본보기).

만들지 않는 것 (= 범위 밖):

- 완성된 블로그 글 본문 — 기획 세트까지만. (글은 `write-tech-blog`.)
- 단편 하나만 — 그건 `plan-blog-topic`.
- 공식 문서로 확인되지 않은 내용을 근거인 양 적는 일.

## 인자 해석

- **상세 요구사항** (필수): 시리즈가 다뤄야 할 내용. 페르소나·목표·꼭 담을 항목·제약이 섞여 들어올 수 있다(`prompts/`의 추출 프롬프트가 그 예다).
- **출력 위치** (필수): 세트를 저장할 **디렉터리**. 없거나 파일 하나를 가리키면, 단편 여러 개가 들어갈 디렉터리를 쓰자고 제안한다.
- **총 편수** (선택): 지시자가 원하는 단편 수. 주면 출발점으로 삼되 절차 2에서 적정성을 따진다. 안 주면 절차 2에서 제안한다.

## 적정 편수 결정 (이 스킬의 핵심)

편수는 지시자의 숫자를 그대로 따르지 않는다. 요구사항의 내용 밀도와 독자 피로도를 보고 **적정 편수를 판단**한 뒤, 지시자와 상호작용해 확정한다(`prompts/002-...`가 "3편 이상 5편 이하에서 밀도와 피로도로 적정 편 수를 판단"하라고 한 것과 같은 방식).

- 한 단편은 한 결정/한 주제를 다룬다. 독립 출판이 가능한 단위로 쪼갠다.
- 다음이면 편수를 **늘리자고** 제안한다: 한 편에 꼭 담을 항목이 너무 많아 분량이 터진다 / 성격이 다른 주제가 한 편에 섞인다.
- 다음이면 편수를 **줄이자고** 제안한다: 단편 하나의 1차 소스가 얇아 독립 글로 서기 어렵다 / 두 단편의 핵심 질문이 거의 겹친다(병합).
- 지시자가 준 편수와 판단이 다르면, **바꾼 편수와 그 근거(어떤 주제를 합치고/쪼개는지)를 제시하고 확인을 받은 뒤** 생성한다. 조용히 다른 편수로 만들지 않는다(Think Before Coding).
- 확인은 `AskUserQuestion`으로 받는다. 지시자가 원래 편수를 고수하면 그 편수로 맞추되, 그때 생기는 무리(분량 초과나 빈약한 단편)를 작성 메모와 폐기·병합 로그에 적어 둔다.

## 절차

성공 기준은 세트가 아래 **검증 체크리스트**를 모두 통과하는 것이다(Goal-Driven Execution).

### 1. 요구사항 파악 (Think Before Coding)

상세 요구사항·출력 위치·(있으면) 총 편수를 확정한다. 1차 소스가 있으면 읽는다. 본보기로 `devops/topics/`의 README와 단편·시리즈 파일을 훑는다.

### 2. 분해와 편수 확정 (적정 편수 결정)

요구사항의 "꼭 담을 항목"을 단편 단위로 쪼갠다. 위 "적정 편수 결정"에 따라 적정 편수를 판단하고, 지시자 편수와 다르면 근거와 함께 `AskUserQuestion`으로 확인받아 확정한다. 확정된 편수만큼 단편의 제목·핵심 질문·덮을 항목을 한 줄씩 먼저 정리한다(생성 전 합의).

### 3. 근거 점검 (외부 자료 참조 원칙)

각 단편 아웃라인의 절이 어떤 근거(1차 소스 §번호 또는 공식 문서) 위에 서는지 정한다. 근거를 못 대는 절은 뺀다. 시리즈 전체에서 한 출처에 모든 단편이 기대지 않는지도 본다.

### 4. 세트 작성 (산출물의 정의)

확정한 편수만큼 단편 설계도를 쓴다. 각 단편은 `plan-blog-topic`의 형식·작성 규칙을 그대로 따르고, 끝에 시리즈 인용 관계 절을 둔다. 그다음 인덱스(`README.md`)를 쓴다 — 단편 목록 표, (있으면) 메타 글 표, 폐기·병합 로그, 작성 가이드. 메타 글이 필요하면 `series-*.md`를 더한다.

단편 사이 "왜"의 중복을 피한다. 메타/시리즈 글은 단편이 답한 근거를 되풀이하지 않고 인과 사슬·누적 효과만 더한다.

### 5. 검증 (Goal-Driven Execution)

- [ ] 각 단편이 `plan-blog-topic` 검증 체크리스트를 통과하는가 (Hook·핵심 질문·관점·근거·타깃·분량·아웃라인·1차 출처·작성 메모)
- [ ] 확정한 편수가 지시자와 합의된 값인가 (다르게 바꿨다면 확인을 받았는가)
- [ ] 지시자의 "꼭 담을 항목"이 시리즈 전체에 빠짐없이, 한 편에 몰리지 않게 분배됐는가
- [ ] 인덱스에 단편 목록 표·폐기 병합 로그·작성 가이드가 있는가
- [ ] 단편 사이 "왜"가 중복되지 않고, 각 단편에 시리즈 인용 관계가 표시됐는가
- [ ] 모든 단편의 참고 출처가 공식 문서·공식 저장소뿐인가
- [ ] 세트 전체 텍스트에 상투어·번역투·키워드 나열이 없는가 (CLAUDE.md "사람이 검증하는 텍스트 작성 규칙")

### 6. 보고

- 한국어로, 사람이 검증하는 텍스트 규칙을 지켜 쓴다.
- 저장한 디렉터리와 파일 목록(단편 N개 + 인덱스), 확정한 편수와 (지시자 값에서 바꿨다면) 그 근거, 폐기·병합한 주제를 짚는다.
- 공식 문서로 확인 못 해 "확인 필요"로 남긴 부분이 있으면 알린다.
- 다음 단계로 각 단편 설계도를 `write-tech-blog`에 넘기면 완성 글을 쓸 수 있음을 한 줄로 안내한다.
- 커밋은 하지 않는다. 사용자가 따로 시킬 때만 한다. (커밋 메시지가 필요하면 `commit-message` 스킬을 쓴다.)

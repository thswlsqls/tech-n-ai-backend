# 8축 점검 항목 (tech-n-ai-backend 맞춤)

각 축의 항목은 이 레포에서 실제로 틀리기 쉬운 지점이다. 축마다 억지로 발견을 만들지 않는다. 항목에 없더라도 코드를 읽다 보이는 결함은 가장 가까운 축에 붙여 다룬다.

## 1. 기술적 정확성·적합성

프레임워크·라이브러리를 공식 문서가 의도한 대로 쓰는가. 판단이 안 서면 기억으로 판정하지 말고 공식 문서(context7 MCP 등)로 확인하고, 확인 못 한 것은 "미확인"으로 남긴다.

- Spring Boot 4 + Jackson 3: `tools.jackson.*` import, autoconfigure 패키지 위치, Spring Batch 6 패키지 이동. 손대기 전에 `~/.claude/projects/-Users-m1-workspace-tech-n-ai/memory/spring-boot-4-migration.md` 확인.
- 트랜잭션 경계: `@Transactional`이 쓰기 경로(Aurora)에 있는가, 읽기 전용 조회에 `readOnly = true`가 빠졌는가, 트랜잭션 안에서 외부 호출(Feign, Kafka 발행)을 하는가.
- TSID: PK 생성이 `@Tsid` + `TsidGenerator` 경유인가. API 경계에서 Long ID가 String으로 직렬화되는가(전역 Jackson 설정을 우회하는 직접 직렬화가 없는가).
- Kafka: 발행-소비 계약(토픽·페이로드)이 양쪽에서 일치하는가. 소비 쪽 Redis 멱등성 처리(7일 TTL)를 우회하는 경로가 없는가.
- CQRS: 쓰기가 MongoDB에 직접 가거나, 읽기 API가 Aurora를 조회하는 우회가 없는가(형제 다수가 그렇게 하고 있다면 patterns.md로).
- gateway 한정: WebFlux/Netty 기반이므로 Servlet·Tomcat·blocking 코드가 섞이지 않았는가.
- LangChain4j(api-agent, api-chatbot): deprecated API, 버전(1.10.0)과 맞지 않는 사용법.
- 예외 처리: `common-exception`의 계층을 쓰는가, 빈 catch나 삼킨 예외로 실패가 조용히 사라지는 경로가 없는가.

## 2. 형제 일관성

같은 부모의 형제 모듈에서 같은 역할 파일을 최소 2개 훑어 다수 패턴을 잡고, 그 대비로 판정한다.

- 패키지 구조: controller / service / repository(writer·reader) / domain 배치가 형제와 같은가.
- 네이밍: `*Entity` / `*Document` / `*HistoryEntity`, DTO·request·response 접미사, 매퍼·컨버터 이름.
- build.gradle: 의존성 선언 방식이 형제와 같은가. JPA 공유 의존성은 `jpa.gradle`을 `apply from:` 하는가(직접 재선언 금지).
- application*.yml: 프로필 구성(local/dev/beta/prod), 포트·데이터소스·Kafka 설정 키의 구조가 형제와 같은가.
- 응답 형식: 컨트롤러 응답 봉투, 에러 응답이 형제와 같은가.
- 형제 다수와 다른 것만 지적한다. 형제 전부가 같은 방식이면 일관성 문제가 아니다.

## 3. 객체지향 설계

Simplicity First가 우선이다. 한 번만 쓰는 코드에 억지로 패턴을 씌우지 않는다.

- 책임 배치: 도메인 판단 로직이 컨트롤러나 매퍼에 새어 있지 않은가. 서비스가 엔티티 내부 상태를 꺼내 조립하는 대신 엔티티에 시킬 수 있는가.
- 캡슐화: setter 남발, 외부에서 컬렉션 필드를 직접 변형하는 코드.
- 불변성: 값 객체·DTO가 불필요하게 가변인가.
- 상속보다 조합: 코드 재사용만을 위한 상속 계층.

## 4. 클린코드

- 이름: 한 번 읽고 의도가 드러나는가. 축약어·번호 붙은 변수·거짓말하는 이름(이름과 실제 동작 불일치).
- 함수 크기: 한 함수가 여러 단계 일을 하면 의미 단위로 분리. 단, 쪼개서 오히려 추적이 어려워지면 두는 것이 맞다.
- 중복: 같은 로직이 모듈 안에서 두 번 이상 복붙된 곳. 모듈을 넘는 중복은 common으로 올릴지 승인 대기로 보고.
- 매직 넘버·문자열: 의미 있는 상수 이름이 필요한 곳만.
- 죽은 코드: 기존 죽은 코드는 언급만 하고 지우지 않는다(Surgical Changes).

## 5. SOLID

위반이 실제 수정 비용이나 결함 위험을 만들 때만 지적한다. 원칙을 지키려고 코드를 부풀리지 않는다.

- SRP: 한 클래스가 서로 다른 이유로 바뀌는가(예: 서비스가 비즈니스 로직 + 외부 API 호출 조립 + 포맷 변환을 다 함).
- OCP: 같은 switch/if-else 분기가 여러 곳에 복제돼 있어 케이스 추가마다 전부 고쳐야 하는가. 분기가 한 곳뿐이면 그대로 두는 것이 맞다.
- LSP: 하위 타입이 상위 계약을 깨는가(예외 추가, 무시되는 오버라이드).
- ISP: 구현체가 대부분 비워 두는 뚱뚱한 인터페이스.
- DIP: api 모듈이 datasource 구현 세부(QueryDSL 타입 등)에 직접 의존해 경계가 새는가. 단, 이 레포는 단순함을 위해 인터페이스 없는 구체 클래스 주입도 쓴다 — 형제 다수 패턴을 따른다.

## 6. 보안

- 시크릿: 코드·application*.yml에 하드코딩된 비밀번호·API 키·토큰. local 프로필의 로컬 인프라 기본값은 거짓 양성이 되기 쉬우니 knowledge에 판정을 남긴다.
- 인젝션: MyBatis `${}` 문자열 치환(반드시 `#{}`), JPQL·네이티브 쿼리 문자열 결합.
- 입력 검증: 외부 입력이 검증 없이 쿼리·경로·외부 호출에 흘러가는 경로.
- 인증·인가: 내부 호출 `X-Internal-Api-Key` 검사를 우회하는 엔드포인트, JWT 검증 없이 노출되는 경로(gateway 라우팅과 대조).
- 민감정보 로깅: 토큰·비밀번호·개인정보가 로그에 찍히는 곳.
- 과다 노출: 엔티티를 응답으로 직접 반환해 내부 필드가 새는 곳, 요청 DTO가 변경 불가여야 할 필드까지 바인딩하는 곳.

## 7. 유지보수성

- 의존 방향: `api → datasource → common → client` 위반. `common-*`·`client-*`가 트리 내 다른 모듈을 의존하면 결함.
- 모듈 경계: 다른 모듈의 내부 구현(리포지토리, 엔티티)을 건너뛰어 직접 쓰는 곳.
- 설정 중복: `jpa.gradle`·루트 build.gradle에 이미 있는 것을 모듈에서 재선언.
- soft-delete·history: 삭제 경로가 soft-delete 규약을 지키는가, `*HistoryEntity` 기록이 빠진 변경 경로가 없는가.
- 테스트: 핵심 경로에 테스트가 아예 없으면 보고(테스트 작성은 즉시 수정 범위 — 단, 결함을 고친 곳에 한한다).

## 8. 가독성

- 한 번 읽고 이해 안 되는 문장형 조건식·중첩 삼항·과한 스트림 체인.
- 주석: CLAUDE.md 텍스트 작성 규칙 위반(상투어, 코드를 반복하는 주석, 낡아서 거짓이 된 주석). 낡은 주석은 결함이므로 고친다.
- 포맷·스타일: 모듈 안에서 들쭉날쭉한 것만. 레포 전체 취향 통일은 하지 않는다.

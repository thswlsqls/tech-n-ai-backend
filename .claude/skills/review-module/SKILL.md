# 모듈 검증·개선 (review-module)

하위 모듈 N개를 받아 코드를 실제로 읽고, 8개 축으로 검증하고, 발견한 결함을 즉시 고치고, 결과를 `memory/`에 쌓는다.

`refactor-module`(동작 불변 정리, 승인 대기)과 다르다. 이 스킬은 **틀리거나 위험한 것을 찾아 고치는** 작업이라 동작 변경이 생길 수 있고, 안전한 수정은 승인 없이 바로 적용한다.

## 모듈 인자 해석

`settings.gradle`은 모듈 이름을 `{parentDir}-{moduleDir}`로 만든다 (`api/auth` → `:api-auth`). 사용자가 어느 표기를 쓰든 받고, 공백·쉼표로 여러 개를 받는다.

- `api-auth :common-kafka datasource/aurora` → 모듈 3개
- 부모가 애매하면(`source` 등) 후보를 보여주고 묻는다.
- 실제 모듈 목록은 추측하지 말고 확인한다: `./gradlew projects` 또는 `find api batch common client datasource -maxdepth 2 -name src -type d | sed 's|/src||'`

## 절차

모듈이 여러 개면 1~6단계를 모듈마다 반복하지 말고, 메모리 로드(1)와 베이스라인(2)은 한 번에 처리한 뒤 모듈 단위로 3~5단계를 진행한다. 재검증(6)과 메모리 축적(7)은 마지막에 몰아서 한다.

### 1. 메모리 로드 (실행할수록 똑똑해지는 핵심)

코드를 읽기 전에 `memory/MEMORY.md`(이 스킬 폴더 기준)를 읽는다. 없으면 첫 실행이므로 인덱스부터 만든다(아래 메모리 구조 참고).

인덱스에서 이번 대상 모듈의 knowledge 파일과 `knowledge/patterns.md`를 읽고 분류한다.

- **검증 완료** — 검증일과 당시 커밋이 적힌 항목은 재검증하지 않는다. 단, 그 모듈 파일이 검증일 이후 수정됐으면(`git log -1 --format=%ci -- <모듈 경로>`) 다시 본다.
- **거짓 양성** — "문제 같지만 의도된 설계"로 판정된 패턴은 다시 지적하지 않는다.
- **반복 결함 패턴** — 다른 모듈에서 이미 발견된 결함 유형은 이번 모듈에서도 가장 먼저 찾아본다. 이 목록이 검증 순서를 정한다.
- **미해결** — 지난 실행에서 승인 대기로 남긴 항목부터 상태를 확인한다.

### 2. 베이스라인 (Goal-Driven Execution)

손대기 전에 대상 모듈이 그린인지 확인한다. QueryDSL이 `src/main/generated`에 생성물을 남기므로 반드시 `clean`을 붙인다.

```bash
./gradlew :<모듈>:clean :<모듈>:build      # 대상 모듈마다
```

- 레드면 그 실패 원인부터 이번 검증의 1순위 결함으로 다룬다(고치는 것이 이 스킬의 일이다).
- 테스트가 없는 모듈은 그 사실을 보고에 적고, 수정 후 검증 수단이 컴파일과 호출부 확인뿐이라는 한계를 명시한다.

### 3. 면밀 분석

모듈의 소스를 실제로 읽는다. 요약이나 기억에 의존하지 않는다. 이 레포의 관례를 기준으로 삼는다.

- CQRS: 쓰기 Aurora(JPA/QueryDSL, `repository/writer/`), 읽기 MongoDB/MyBatis(`repository/reader/`), Kafka 동기화 + Redis 멱등성
- 네이밍: `*Entity` / `*Document` / `*HistoryEntity`, TSID PK, Long→String 직렬화
- 의존 방향: `api → datasource → common → client` (`common-*`·`client-*`는 트리 내 다른 모듈에 의존하지 않음)
- Spring Boot 4 + Jackson 3 함정: `~/.claude/projects/-Users-m1-workspace-tech-n-ai/memory/spring-boot-4-migration.md` 먼저 확인

**형제 기준선 잡기**: 대상 모듈과 같은 부모의 형제 모듈(예: `api/auth`의 형제는 `api/*` 나머지)에서 같은 역할 파일(컨트롤러, 서비스, 설정, build.gradle)을 훑어 다수 패턴을 파악한다. 일관성 판정은 이 다수 패턴 대비로 한다. 형제 다수가 같은 문제를 공유하면 "모듈이 틀린 것"이 아니라 "레포 공통 패턴"이므로 patterns.md에 적고 보고로 돌린다.

### 4. 8축 검증

`references/checklist.md`를 읽고 축별 점검 항목을 따라간다. 축 요약:

1. **기술적 정확성·적합성** — 프레임워크·라이브러리를 올바르게 쓰고 있는가 (트랜잭션 경계, Jackson 3, TSID 직렬화, Kafka 멱등성 등)
2. **형제 일관성** — 형제 모듈의 다수 패턴과 어긋나는 구조·네이밍·설정이 없는가
3. **객체지향 설계** — 책임 배치, 캡슐화 (단, 한 번만 쓰는 코드에 억지 적용 금지)
4. **클린코드** — 이름, 함수 크기, 중복
5. **SOLID** — 위반이 실제 수정 비용을 만들 때만 지적 (Simplicity First가 우선)
6. **보안** — 시크릿 노출, 인젝션, 입력 검증, 민감정보 로깅, 내부 API 키 취급
7. **유지보수성** — 의존 방향 위반, 모듈 경계 누수, 설정 중복
8. **가독성** — 한 번 읽고 이해되는가, 주석이 텍스트 작성 규칙을 지키는가

발견 항목은 한 줄씩 적는다: `[파일:라인] 축: <무엇이 왜 문제인가> → <어떻게 고칠 것인가>`

과장하지 않는다. 축마다 억지로 하나씩 찾아내지 않는다. "이 축은 문제 없음"도 정직한 결과이고 메모리에 그렇게 적는다.

### 5. 즉시 개선 (Surgical Changes 유지)

발견 즉시 고치는 것이 기본이다. 단, 영향 등급으로 가른다.

- **즉시 수정** — 모듈 내부에 갇힌 결함: 잘못된 구현, 보안 결함, 이름·중복·책임 배치, 형제와 어긋난 내부 구조. 고친 뒤 6단계로 검증한다.
- **보고 후 승인 대기** — 외부 계약을 바꾸는 것: 공개 API 시그니처·응답 형식, DB 스키마·엔티티 필드, Kafka 이벤트 계약, 다른 모듈이 쓰는 public 메서드, 의존성 추가·제거. 발견 내용과 수정안만 보고에 적는다.

고친 줄은 전부 4단계 발견 항목으로 곧장 설명돼야 한다. 결함과 무관한 인접 코드 정리를 끼워 넣지 않는다. 기존 죽은 코드는 언급만 한다.

### 6. 재검증

```bash
./gradlew :<모듈>:clean :<모듈>:build      # 수정한 모듈마다
```

`common-*`·`datasource-*`·`client-*`를 고쳤으면 의존 모듈이 깨질 수 있으므로 전체를 다시 빌드한다.

```bash
./gradlew clean build
```

레드면 내 변경이 원인이다. 되돌리거나 고쳐서 그린으로 만든 뒤 끝낸다. 레드인 채로 보고하지 않는다.

### 7. 메모리 축적

실행을 마치면 이 스킬 폴더의 `memory/` 아래에 결과를 남긴다.

```
memory/
├── MEMORY.md                  # 인덱스 — knowledge·runs 한 줄 요약 목록
├── knowledge/<모듈>.md        # 모듈별 누적 지식 (예: api-auth.md, common-kafka.md)
├── knowledge/patterns.md      # 레포 공통 — 반복 결함 패턴, 레포 전역 거짓 양성
└── runs/<YYYYMMDDHHMMSS>.md   # 실행 1회 보고서
```

knowledge 파일 항목 형식:

```markdown
## 검증 완료
- <축>: <문제 없음 판정 또는 확인한 사실 한 줄> (검증일 YYYY-MM-DD, 커밋 <hash>)

## 거짓 양성 (다시 지적하지 말 것)
- <문제처럼 보이는 패턴> — 실제로는: <왜 의도된 설계인지> (판정일 YYYY-MM-DD)

## 고침
- <결함 한 줄> → <수정 한 줄> (수정일 YYYY-MM-DD)

## 미해결
- <발견했지만 못 고친 것> — 이유: <승인 대기 | 범위 밖 | ...>
```

`patterns.md`에는 두 모듈 이상에서 나온 결함 유형과, 레포 전체에 해당하는 거짓 양성을 적는다. 다음 실행이 이 목록으로 검증 순서를 잡는다.

runs 보고서에는 대상 모듈, 축별 발견 수, 고친 것, 승인 대기, 메모리에 새로 적은 것을 적는다. 이미 있는 knowledge 항목과 겹치면 새로 만들지 말고 갱신하고, 틀렸다고 판명된 항목은 지운다. 새 파일·항목을 만들면 `MEMORY.md` 인덱스에 한 줄을 추가한다.

### 8. 보고

한국어로, CLAUDE.md의 "사람이 검증하는 텍스트 작성 규칙"을 지켜 쓴다.

- 고친 것: 무엇이 왜 문제였고 어떻게 고쳤는지, 빌드·테스트 결과
- 승인 대기: 외부 계약을 바꾸는 수정안과 근거
- 문제 없음: 검증했지만 결함이 없던 축 (다음 실행이 건너뛸 수 있도록)
- 메모리: 이번에 쌓인 지식 요약

커밋은 하지 않는다. 커밋 메시지가 필요하면 `commit-message` 스킬을 쓴다.
